# auth

Registration, login, logout, the authentication cookies and the current user (`/api/auth/*`).

## Built so far

| Route                             | Requirement    | Access                                 |
| --------------------------------- | -------------- | -------------------------------------- |
| `POST /api/auth/register`         | ACC-01         | Public                                 |
| `POST /api/auth/login`            | ACC-04, ACC-05 | Public                                 |
| `POST /api/auth/logout`           | ACC-06         | Public (see below)                     |
| `POST /api/auth/refresh`          | ACC-06         | Public (the refresh cookie is checked) |
| `GET /api/auth/me`                | ACC-04, ACC-19 | Any logged-in user                     |
| `PATCH /api/auth/change-password` | ACC-08         | Any logged-in user                     |
| `DELETE /api/users/me`            | ACC-12         | Registered users (`user` role)         |

`AuthCookiesService` sets, clears and reads the two authentication cookies (ACC-19). `AuthTokensService` signs and checks the tokens. `SessionsService` owns the `sessions` collection (ACC-06). `JwtAuthGuard` is the guard that protects every route (ACC-04).

## Design decisions

- **Registering does not log the user in.** The route answers 201 with the new account and sets no cookie. The requirement asks for an account, not a session, and login with its lockout rules is ACC-04. The frontend sends the user to the login page next.
- **This module never touches the `users` collection.** `AuthService` calls `UsersService`, which owns the collection and hashes the password. Every way of creating an account therefore hashes in one place.
- **The client sends only `name`, `email`, `password` and `acceptedTerms`.** The role (`user`) and the status (`active`) are set by the server. Any other field, such as `role`, is rejected with 400 by the global `ValidationPipe`.
- **Consent is stored as a date.** `acceptedTerms` must be exactly `true`. The service then saves the time of the request in `consentAcceptedAt`, so the account records when the consent was given.
- **An email that is already registered answers 409** with the message "This email is already registered", as the response conventions in the specification say. The requirement asks for this message, so the route does tell a guest that an email has an account.
- **The email is trimmed and lowercased before it is checked**, so `Sara@Example.com` and `sara@example.com` are the same account.
- **Passwords are limited to 72 characters** (`PASSWORD_MAX_LENGTH`). The workbook sets only the minimum. bcrypt reads only the first 72 bytes, so a longer password would be cut without the user knowing.

## Login and the authentication guard (ACC-04)

- **Every route needs a login unless it is marked `@Public()`.** `JwtAuthGuard` and `RolesGuard` are registered as global guards (`APP_GUARD`) in `AuthModule`, in that order: first who is calling, then whether that role may do it. A feature module only adds `@Public()` or `@Roles(...)` to its routes. This lives in `auth/` and not in `common/`, so no shared-layer pull request was needed.
- **The tokens travel only in httpOnly cookies** (ACC-19). Login sets `access_token` (path `/`, `ACCESS_TOKEN_MINUTES`) and `refresh_token` (path `/api/auth`, `SESSION_INACTIVITY_MINUTES`) and returns the user in the body, with no token in it. The `role` in the body tells the frontend which home page to open.
- **Two secrets, so one token can never pass as the other.** The access token is signed with `JWT_ACCESS_SECRET` and the refresh token with `JWT_REFRESH_SECRET`. Only `HS256` is accepted, so a token that names another algorithm (`none`) is refused. Both secrets are checked when a token is made or read, with a message that names the missing variable. They are not yet checked at startup: that is a shared-layer change in `config/` for its own pull request.
- **The token carries the user id and the session id.** The guard reads the account from the database on every request, so a suspension, a deactivation or a role change applies at once and not when the token expires. The price is one query per request; with a 10-minute token this is the safer choice for a booking site.
- **One message for every failed login.** An unknown email, a wrong password and a deactivated account (ACC-12) all get 401 "Invalid email or password". For an unknown email the service still compares the password with a hash that no password matches, so the answer does not come faster and the response time does not show which emails are registered.
- **A suspended account gets 403 "Your account is suspended"**, as the requirement asks, but only after the password is right, so the suspension is not shown to someone who does not know the password. The guard also refuses a suspended user who still has a valid token.
- **A missing, expired or invalid token answers 401 "You must log in to do this"**, whatever the reason, so the answer does not help someone who forges tokens.
- **`GET /api/auth/me` is how the frontend learns the current user** (ACC-19), because it cannot read the httpOnly cookie. It stays as it is: ACC-19 adds proof, not a route (see "Authentication cookies and no browser storage" below).
- **Swagger:** log in with `POST /api/auth/login` in Swagger UI. The browser keeps the cookies and sends them with every later request, including the ones made by "Try it out". If the browser does not keep them over `http://localhost`, set `COOKIE_SECURE=false` in your own `backend/.env`.

## Account lockout (ACC-05)

The 5th wrong password in a row locks the account for 15 minutes (`MAX_FAILED_LOGIN_ATTEMPTS` and `LOCKOUT_MINUTES` in `auth.constants.ts`). The state is `failedLoginAttempts` and `lockedUntil` on the user. Neither field ever leaves the API.

- **The 5th failure already gets the lockout answer.** The user does not have to try a 6th time to find out. The answer is **429**, which keeps it apart from 401 (wrong password) and 403 (suspended), so the frontend can tell the three apart by the status. The message says how many minutes are left, rounded up so nobody tries too early: "Too many failed login attempts. Your account is locked. Try again in 15 minutes."
- **A locked account is refused before the password is looked at.** Even the right password gets 429 until the lock ends. The refused attempts are not counted and do not move the end of the lock, so an attacker cannot extend it and the owner knows exactly when it ends.
- **When the lock ends, the count starts again.** The first login after the lock clears `lockedUntil` and sets the count to 0, so the user gets 5 new attempts and not just one. A successful login also sets the count to 0, so the failures have to be in a row. A login only writes to the database when there is something to reset.
- **The count is one atomic `$inc`.** Ten wrong passwords that arrive at the same moment cannot read the same number and slip past the limit. The lock is set with a filter that matches only an account with no active lock, so the first failure over the limit sets it and the others leave it alone.
- **Who is counted.** Only real accounts. An unknown email and a deactivated account (ACC-12) are never counted or locked, so they still answer a plain 401 and cannot be told from "no account". A suspended account is counted like any other, because it is a real account; its right password still gets 403 and is not counted as a failure, and it does not reset the count either, because it is not a successful login. The lock comes before the suspension message.
- **Known trade-off.** The lockout message shows that the email has an account, but only to someone who made 5 wrong attempts on it. The requirement asks the system to "show a lockout message", so it is kept. The same 5 attempts also let anyone lock a known email for 15 minutes. That follows from the rule as the requirement states it; limiting attempts per IP address as well would be a separate feature.
- **Where it lives.** The rule is in `AuthService.login`. The three database operations (`recordFailedLogin`, `clearExpiredLock`, `resetFailedLogins`) are in `UsersService`, which owns the `users` collection. The limits are constants and not environment variables, so no shared-layer change was needed.
- **Not built here:** a `Retry-After` header. The exception filter builds every error response and sets no headers, so adding one is a shared-layer change for its own pull request. The message already says how long is left.

## Change password (ACC-08)

`PATCH /api/auth/change-password` takes `currentPassword` and `newPassword` and returns the account (200).

- **The current password is always checked**, even right after login, so someone who only has the session (a computer left unlocked) cannot take over the account. A wrong one answers **400** "The current password is incorrect", not 401: the user is logged in, and a 401 would make the frontend think the session ended.
- **The new password follows the registration rule** (`PASSWORD_PATTERN`, at most 72 characters). A broken rule is a normal validation error with `newPassword` in `errors`. The current password is not checked against the rule, so an older or temporary password still works.
- **The new password must differ from the current one** (400 "The new password must be different from the current password"). This is checked only after the current password is right, so the answer tells nothing to someone who does not know it. It matters most after a temporary password (ACC-07a, ACC-13). The workbook does not ask for it; it is one string comparison.
- **It clears `mustChangePassword`.** An admin reset (ACC-07a) or a new moderator account (ACC-13) sets the flag. Login and `GET /api/auth/me` return it in the account, so the frontend can open this route at once. The backend enforces it: while the flag is `true`, every other route answers 403 "You must change your temporary password first" (see "Temporary password" below). Once this route succeeds, the same session can use every route at once.
- **The hashing and the write are in `UsersService.updatePassword`**, which owns the `users` collection. It sets the new hash and `mustChangePassword: false` in one update. `findEntityByIdWithPasswordHash` is the lookup for the check; neither method is exposed by a controller.
- **This session stays logged in; every other session of the account ends.** Someone who stole a session cookie loses it when the owner changes the password. The session that made the change is read from its access cookie, as logout reads it (`AuthTokensService.readClaims`), and kept; `SessionsService.revokeAllOfUser` sets `revokedAt` on all the others in one `updateMany` whose filter always names the user. Their access and refresh cookies get 401 at once. If the access cookie cannot be read, or names another user, the route answers 401 "You must log in to do this" and changes nothing.
- **The password is saved first, then the other sessions end.** If the second step fails, the new password is in place but the old sessions stay alive until they log out or run out (30 minutes idle). The other order would be worse: sessions ended but the old password still valid. Neither step is skipped on a normal request; they are not one transaction because they are two collections.
- **Wrong current passwords are not counted for the lockout** (ACC-05). The lockout protects the login of someone who has no session; this route already needs one.

## Deactivate my own account (ACC-12)

`DELETE /api/users/me` with `{ "currentPassword": "..." }` closes the account of the logged-in user and answers **204** with no body. `AccountDeactivationController` (`@Controller('users')`, `@ApiTags('users')`) and `AccountDeactivationService` in this module.

**Decisions** (each one is listed in the pull request for review):

- **D1. The route lives in the auth module, not in users.** It reads bookings, hides posts and itineraries and ends sessions. The blog and itineraries modules import `UsersModule`, so `UsersModule` cannot import them without a cycle. Only `AppModule` and `AdminModule` import `AuthModule`, so `AuthModule` can import `BlogModule`, `ItinerariesModule`, `FlightBookingsModule` and `HotelBookingsModule`. The controller uses the `users` path and tag, so Swagger shows it with `GET` and `PATCH /api/users/me`.
- **D2. "After confirmation" means the current password.** The body is only `currentPassword` (the same rules as in ACC-08: a text, not empty, at most 72 characters, the password rule is not checked). A wrong one answers 400 "The current password is incorrect" and changes nothing; it is not counted for the lockout (ACC-05). The user cannot undo a deactivation, so a stolen session alone must not be enough. The frontend's confirmation dialog (Milestone 2) is on top of this. The client never sends a status or a flag: any other property is 400.
- **D3. "Upcoming confirmed bookings" means any booking with status `confirmed`**, flight or hotel. No date arithmetic: GEN-11's completion jobs move a confirmed booking to `completed` once its trip is over, so one that is still `confirmed` is not over yet. A completed, expired or cancelled booking does not block.
- **D4. A live hold blocks it too.** A booking `pending_payment` whose `holdExpiresAt` is still in the future: a payment inside the hold would confirm a booking of an account that can no longer log in (money taken, no access to the e-ticket). The requirement names only confirmed bookings; this is an extra rule with its own message. A hold that has ended does not block (a late payment is refunded, PAY-03).
- **Only registered users.** `@Roles(Role.User)`: an administrator or a moderator gets 403. Admin accounts are seeded and moderator accounts belong to a provider; neither closes itself here.

**Answers.** 204 (cookies cleared); 400 wrong password or invalid body; 401 not logged in; 403 not a registered user, suspended, or a temporary password to change first (`JwtAuthGuard`); 409 with one of these messages (`auth.constants.ts`):

- `ACCOUNT_HAS_CONFIRMED_BOOKINGS_MESSAGE`: "You have upcoming confirmed bookings. Cancel them or wait until the trips are over, then deactivate your account"
- `ACCOUNT_HAS_UNPAID_BOOKING_MESSAGE`: "You have a booking waiting for payment. Pay it, or wait until its hold ends, then deactivate your account"
- `ACCOUNT_CHANGED_MESSAGE`: "Your account was changed by another request. Please try again"

**The order of the steps is the design** (`AccountDeactivationService.deactivate`). Everything that can refuse comes first, everything that can be repeated comes before the status change, so a failure never leaves the user stuck:

1. Read the account with its hash. Missing, not a `user` or not `active`: 401 (a backstop; the guards already refuse these).
2. Compare the current password (bcrypt). Wrong: 400.
3. Confirmed flight or hotel booking (both read at once): 409.
4. Live flight or hotel hold (both read at once): 409 with the unpaid message.
5. Hide the content: `PostsService.markAuthorDeactivated` and `ItinerariesService.markOwnerDeactivated`. Each is one `updateMany` filtered by this user only, with `timestamps: false`, and idempotent, so if a later step fails the user simply tries again. These are the only multi-document writes.
6. The status change: `UsersService.deactivateOwnAccount`, one conditional update from `active` that also sets `deactivatedAt`. `null` (an admin suspended the account at the same moment): 409 "Your account was changed by another request".
7. End every session: `SessionsService.revokeAllOfUser(userId, now)`, this one included. If it fails, the error is logged (the user id only, never the password or the hash) and the request still succeeds: `JwtAuthGuard` already refuses a deactivated account on every request, and refresh refuses it too.

The controller then clears both cookies (`AuthCookiesService.clearAuthCookies`, like logout). After that the login with the right password answers the plain 401 "Invalid email or password", the old cookies get 401, and an admin's reactivate answers 409.

**Known limits.**

- Two requests at the same moment can slip through: a hold created in another session between steps 3-4 and step 6. The window is a few milliseconds and the account is refused by the guard right after step 6. Not fixed here (it would need a transaction across three collections).
- If step 6 answers 409 because an admin suspended the account at that moment, the posts and itineraries are already hidden while the account is only suspended, and a later reactivation (ACC-16) does not show them again. It needs an admin and a user acting in the same moment; it hides content, it never shows hidden content. Not fixed here.

**Not done here.** The email stays taken (the unique index), so it cannot be used to register again. Nothing is notified, cancelled or refunded: confirmed bookings block the deactivation instead. The public reviews of a hotel (HTL-24) show "Deleted user" for a deactivated author, as comments do (see the users README). The user cannot reopen the account and an admin cannot reactivate it.

**Tests:** `account-deactivation.service.spec.ts` (every branch and the order of the calls), `account-deactivation.controller.spec.ts` (route, role, 204, cookies), `dto/deactivate-account.dto.spec.ts`, and `test/users-deactivate-account.e2e-spec.ts`.

## Temporary password (ACC-13, ACC-07a)

An account with a temporary password set by an admin (a new moderator, ACC-13, or a reset, ACC-07a) has `mustChangePassword: true` until it sets its own password with `PATCH /api/auth/change-password`. Until then, **every route that needs a login except two answers 403 "You must change your temporary password first"** (`PASSWORD_CHANGE_REQUIRED_MESSAGE`).

- **Why the guard.** The requirements say the account _must_ set a new password, and GEN-13 says business rules are enforced by the backend whatever the frontend does. Milestone 1 is evaluated through Swagger with no frontend, so a flag alone enforced nothing: a moderator could use a temporary password for ever. This reverses the earlier "flag only" decision. `JwtAuthGuard` is global and already loads the account on every request, so the check costs no extra query and no route can forget it.
- **Why 403 and not 401.** The caller is logged in and the session is valid; a 401 would make the frontend think the session ended and send it to the login page. 403 says "you may not do this yet", and the message says why.
- **The allow-list is exactly two routes,** marked with `@AllowTemporaryPassword()` (`auth/decorators/allow-temporary-password.decorator.ts`), which the guard reads from the handler and the controller (`getAllAndOverride`, like `@Public()`):
  - `PATCH /api/auth/change-password`, the way out;
  - `GET /api/auth/me`, so the frontend learns who is logged in and sees the flag.
    Login, register, logout and refresh are `@Public()`, so the guard does not run for them: the account can still log in, refresh its session and log out. No other route carries the decorator, and a new route is restricted unless someone adds it in plain view of the reviewer.
- **The order of the checks.** No token, a session that is not live or a missing account: 401. Suspended: 403 "Your account is suspended". Not active: 401. Only then the temporary password: 403 with its own message. So a suspended account with a temporary password is told it is suspended, and a guest still gets 401. `RolesGuard` runs after `JwtAuthGuard`, so the temporary-password 403 comes before any role check.
- **Two 403 messages exist now** on the routes that need a login: suspended and temporary password. A frontend tells them apart by the message.
- **It applies at once.** The flag is read with the account on every request. `change-password` clears it, so the same session works on the next request without logging in again; an admin reset sets it and ends the account's sessions. Nothing is cached.
- **Old documents.** A missing field counts as `false` (`=== true`). Any account that already has the flag in a database, for example a moderator created before this change, is restricted from its next request until it changes its password.
- **Tests:** `guards/jwt-auth.guard.spec.ts` (the flag on a plain route, the decorator on the handler and on the class, the flag false or missing, suspended or inactive accounts with the flag, `@Public()`), `decorators/allow-temporary-password.decorator.spec.ts`, and the e2e suites `test/temporary-password.e2e-spec.ts` (routes across modules), `test/auth-change-password.e2e-spec.ts`, `test/admin-moderators.e2e-spec.ts` and `test/admin-reset-password.e2e-spec.ts`.

## Logout, refresh and the 30-minute limit (ACC-06)

A login starts a **session**, one document in `sessions` (`userId`, `refreshTokenHash`, `lastActivityAt`, `expiresAt`, `revokedAt`), as the data model in the specification describes. Both tokens carry its id (`sid`). A valid signature is not enough to get in: the guard also asks the session whether it is still live.

- **Logout revokes the session on the server.** It sets `revokedAt`, so the access token stops working at once and not when it expires after `ACCESS_TOKEN_MINUTES`, and the refresh token stops working too. The route also clears both cookies. It answers **204**.
- **Logout is `@Public()` and never fails.** The requirement says a logged-in user logs out, but an access token lasts only `ACCESS_TOKEN_MINUTES`. If logout needed a valid one, a user whose token just expired would get 401, the cookies would stay, and the refresh token would stay valid on the server. So logout reads the cookies itself: the refresh cookie is sent to `/api/auth`, and an expired token still ends its session as long as its signature is right. A token that is not ours revokes nothing. Logging out twice, or with no cookie, is a harmless 204.
- **Logout ends one session, not all of them.** Another browser of the same user stays logged in. "Log out everywhere" is not in the requirements.
- **The 30 minutes are counted on the session.** `expiresAt` is `lastActivityAt` plus `SESSION_INACTIVITY_MINUTES`. Every authenticated request that gets through the guard moves it forward (one indexed `updateOne`), so a session with no authenticated request for 30 minutes has run out and the next request gets 401 "You must log in to do this". The same query refuses a revoked session, a session of another user and a session that does not exist, so they all answer alike. The inactivity limit stays an environment variable, as in ACC-19.
- **A TTL index on `expiresAt` deletes finished sessions**, revoked ones included, so the collection does not grow. MongoDB runs the cleanup about once a minute, so the guard never relies on it: it checks `expiresAt` itself.
- **`POST /api/auth/refresh` gets new tokens without the password.** It needs only the `refresh_token` cookie, which is why it is `@Public()`: the access token is exactly what has expired by then. On success both cookies are replaced and the account is returned, like login. The section 8 table of the project description does not list the route, but the specification describes a refresh (ACC-19: "Logging in or refreshing issues new tokens"), and without it a session could not last longer than one access token.
- **A refresh token works once.** The session keeps the SHA-256 hash of the current refresh token. A refresh replaces it with the hash of the new token in a single atomic update that matches only the old hash, so of two refreshes with the same token at the same moment exactly one succeeds. The loser gets 401. A random `jti` in every refresh token makes sure two tokens made in the same second are never the same text. Only the hash is stored, so a leaked database does not hand out working tokens.
- **A refresh counts as activity**, like any authenticated request. The frontend should call it because a user action got a 401, not on a timer; a timer would keep an idle session alive for ever.
- **Every refresh failure is the same 401.** No cookie, a broken or expired token, a revoked or idle session, a token that was already used, a deleted or deactivated account. A suspended account gets 403, like the guard.
- **Every login makes a new session** and there is no limit per user. Old sessions end by logout, by a password change or an admin password reset (ACC-08, ACC-07a), or by the TTL index. A cap would be a feature of its own.
- **What this changes for a deployment.** Tokens issued before ACC-06 have no session id and are refused, so everybody logs in again once. The `sessions` collection and its indexes are created by Mongoose when the API starts.
- **Known trade-offs.** If the same browser refreshes twice at once (two tabs), the second request gets 401 although the cookie it will have next is fine; the frontend can retry `GET /api/auth/me` once. If a used refresh token is sent again, the session is not revoked. That would catch a stolen token, but it would also log out the user who lost a race; it is not required here.
- **Where it lives.** Logout and refresh are in `AuthService`, the guard check is in `JwtAuthGuard`, and every database operation is in `SessionsService`. No environment variable was added and nothing in the shared layer changed.

## Authentication cookies and no browser storage (ACC-19)

ACC-19 needed no production change: the cookies (ACC-04, ACC-06) already met it. It adds the proof, in `test/auth-cookies.e2e-spec.ts` against the real app setup, and one unit test in `auth-cookies.service.spec.ts`. The e2e file pins the cookie settings in `test/support/auth-cookie-env.ts` (10 and 30 minutes, `COOKIE_SECURE=true`, `COOKIE_SAME_SITE=lax`), so a local `backend/.env` cannot change the exact attributes it checks. It builds the `Cookie` header by hand, as a browser does, because the supertest agent's jar drops `Secure` cookies over plain http.

**Swagger UI keeps nothing in the browser.** `setupSwagger` does not set `persistAuthorization`, so what someone types into the Authorize box is not kept in `localStorage` and is not written as a JavaScript cookie. `test/app.e2e-spec.ts` ("does not let Swagger UI persist the authorization in the browser (ACC-19)") fails if the option comes back. Logging in with `POST /api/auth/login` never needs the Authorize box.

**CORS names `FRONTEND_URL` on every answer**, also to a foreign origin, which the browser then refuses (`app.setup.ts`, fixed `origin`). Allowing it with a list instead would send no header at all to a foreign origin; that is optional hardening in the shared layer.

**The frontend contract (Milestone 2).**

- Send every request to the API with `credentials: 'include'`, so the browser sends the cookies.
- Learn the user from `GET /api/auth/me` when the app starts and after login. Keep the user only in memory (React state), never in `localStorage`, `sessionStorage`, `document.cookie` or IndexedDB.
- On a 401, call `POST /api/auth/refresh` once and repeat the request. If the refresh fails too, go to the login page.
- Logout is `POST /api/auth/logout`, then clear the in-memory user.
- JavaScript cannot read the cookies and must not try. `proxy.ts` reads `access_token` on page requests only to decide redirects; the API checks the token on every request.

## Guests and restricted actions (ACC-10)

- **The backend's part is one clear refusal.** A guest who tries a restricted action (book, review, post, or anything else that needs an account) gets 401 "You must log in to do this" from `JwtAuthGuard`, before any validation or database work. The message is the same on every route and for a missing, expired or forged token, so the frontend can rely on it.
- **Sending the guest to the login page and back to the action is the frontend's job** (Milestone 2). The frontend keeps the page and the action the guest wanted, opens login, and repeats the request once `POST /api/auth/login` has set the cookies. The backend needs nothing extra for this: the repeated request is a normal request with a valid cookie.
- **No new production code.** ACC-04 already makes every route private unless it is marked `@Public()`, so ACC-10 adds tests that keep it that way.
- **The tests read the real route table** (`test/guest-access.e2e-spec.ts`) instead of a hand-made list. Every route that is not public must answer a guest with 401 and document the 401 in Swagger, so a booking, review or comment route added later is checked without anyone editing the test.
- **A route that changes data cannot become public by accident.** The test allows only the account routes and the Stripe webhook (`PUBLIC_WRITES`). A pull request that adds a new public route that changes data must add it to that list, in plain view of the reviewer. The same test also keeps the private areas (bookings, payments, refunds, notifications, accounts, private itineraries) closed to guests.

## Owner-only bookings and private itineraries (ACC-11)

- **The rule.** A booking or a private itinerary belongs to one user and only that user opens or changes it. The only exceptions are the ones in the workbook: an administrator may read every booking (ACC-17) and a moderator the bookings of their own hotel or airline (FLT-29, HTL-22). Nobody else gets in, and no role gets into a private itinerary: an administrator or a moderator who asks for one gets 403 like any other user.
- **Itineraries: missing is 404, someone else's is 403.** The service loads the record by id (404 if there is none) and then compares its owner with the user from the login cookie (403). The pattern is `findOwnedOrThrow` in `ItinerariesService`. A malformed id is 400 (`ParseObjectIdPipe`), before any lookup.
- **Bookings: someone else's is the same 404 as a missing one.** Every booking-family service reads with one filter on the id and the logged-in owner (`{ _id, userId }`), so another user's booking, payment, refund or review answers exactly like an id that does not exist, and an id reveals nothing. The answer is the module's own message: "Booking not found", "Payment not found", "Refund not found" or "Review not found".
- **The owner always comes from the login, never from the client.** A request cannot send an owner id, and a list filters by the owner id of the logged-in user, so a list can never contain someone else's records.
- **What this issue adds.** `GET /api/users/me` (section 8 lists it under ACC-11) and `test/owner-access.e2e-spec.ts`. The tests run the five itinerary routes as the owner, another user, an administrator and both moderator types, on private and public itineraries, and check that nothing changed after a refused request. No production code of `itineraries` changed: its ownership check was already correct, and the tests now keep it that way.
- **The booking half, audited and tested (`test/owner-access-bookings.e2e-spec.ts`).** An audit of every booking-family route found no hole, so no production code changed:
  - **Owner routes** (`@Roles(Role.User)` and the `{ _id, userId }` filter): `GET /api/flight-bookings/:id`, its `e-ticket`, `cancel` (GET and POST), `seat-map` and `PATCH .../seat` (FLT-28); `GET /api/hotel-bookings/:id`, its `cancel` (GET and POST) and `POST .../review`; `PATCH` and `DELETE /api/reviews/:id`; `POST /api/payments` (the booking is in the body), `POST /api/payments/:id/retry`, `GET /api/payments/:id`; `GET /api/refunds/:id`; `GET /api/bookings/:type/:id/policies` and `POST .../accept-policies`. The owner is served on the routes that only read, or gets the 409 of its record's state where the route would otherwise write (the routes that change data, such as a cancellation, are tested for their owner in their own suites); another user gets the 404 of a missing id, every staff role gets 403 from the role check, and a guest 401. Refused requests change nothing.
  - **Lists** `GET /api/flight-bookings` and `GET /api/hotel-bookings` filter by the logged-in owner: another user sees none of the owner's bookings, and staff get 403.
  - **The owner comes from the login:** a `userId` in the query of a list, or in the body of `POST /api/flight-bookings`, `POST /api/flight-bookings/hold`, `POST /api/hotel-bookings` or `POST /api/payments`, is refused with 400.
  - **Admins** read every booking only through `GET /api/admin/bookings` (ACC-17, `@Roles(Role.Admin)`); on the owner routes they get 403 like other staff.
  - **Moderators** read only the bookings of the provider in their own `assignment` (read from their account, never from the request): `GET /api/flights/:id/bookings` and `.../passengers/export` (FLT-29), `GET /api/hotels/:id/reservations` (HTL-22). The moderator of another airline or hotel gets 403. Two moderator routes write, so the right moderator never sends them in this test: `POST /api/flights/:id/cancel` (it would cancel the booking) and `POST /api/reviews/:id/reply` (HTL-26, tested in `test/hotel-review-replies.e2e-spec.ts`). On the reply, every role but a hotel moderator gets 403 from the role check, the moderator of another hotel gets 403 "You do not manage this hotel" (`HotelsService.findManagedEntityOrThrow`), and the test checks after every refusal that the review still has no reply.
  - **Completeness.** The test reads the route table of the running app, as `guest-access` does: every route of the booking areas, and every route whose path names bookings, reservations, passengers, payments, refunds or reviews, must be in its matrix, and only the Stripe webhook and the public reviews of a hotel (HTL-24) may be public. A new booking route fails the test until it is added with its expected answers. Its limits are those of `guest-access`: a handler inherited from a base controller is not found, and a booking route whose path names none of those words would slip past, so a new booking area must be added to `BOOKING_AREAS` in the test.
  - **Safety.** The records are seeded straight into the `-test` database and deleted one by one by id. The app's scheduled jobs are stopped, so they cannot touch other suites' records. Every gateway method that calls Stripe is replaced by a stub that fails, and the test checks that none was called.
