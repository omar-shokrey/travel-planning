# Blog Module

## Design decisions

- Blog posts are stored in the `posts` collection using the `BlogPost` Mongoose schema.
- Each post stores the authenticated user's `authorId`; the client cannot choose the author.
- `POST /api/posts` is the route of section 8 of the project description. Listing, the post page, tags and search (BLG-02, BLG-03, BLG-08, BLG-09) add their own routes and indexes.
- A post can be saved as either `draft` or `published`.
- New posts default to `draft` when no status is provided. `status` and `tags` sent as `null` answer 400 (the DTO validates them whenever they are sent, and the schema requires `status`), so no post is stored without a status.
- Published posts receive a `publishedAt` timestamp when they are created.
- `GET /api/posts/mine` (BLG-03) lists the logged-in user's own posts, drafts and published, newest first (`createdAt`, then `_id`), 10 per page by default (GEN-05). It is for the `user` role, like creating a post. The filter is the author id from the login, so nobody can see someone else's drafts. Each row (`MyPostResponseDto`) has the id, title, status, `moderation` (GEN-10), `publishedAt` (left out for a draft), `createdAt`, `updatedAt`, `likeCount` and `commentCount`; the body, tags and images belong to the post page (BLG-02). Index: (`authorId`, `createdAt`, `_id`).
- The post schema has `commentCount` and `likeCount` (default 0), written exactly as in the BLG-05 and BLG-06 PRs, which keep them in step with the `comments` and `likes` collections. "My posts" only reads them. Posts are read hydrated, not with `lean()`, so the default 0 applies to posts stored before the counters existed.
- The `mine` route is declared before any `GET /api/posts/:id` route (BLG-02), so `mine` is never read as a post id.
- **Moderation (GEN-10).** A post has `moderation`: `visible` (the default) or `hidden`. Only an admin changes it, through `PATCH /api/admin/content/post/:id` or by resolving a report (`admin` module); no blog DTO accepts it. It is separate from `status`: the author can still edit, unpublish or republish a hidden post, and it stays hidden until an admin shows it again. Posts are read hydrated in "my posts", so a post stored before the field existed reads as `visible`; `findPublishedSummary` (read with `lean()`) treats a missing value as `visible` too.
- **A hidden post is visible only to its author and to admins.** Today that means: "my posts" (BLG-03) still lists it for its author, with `moderation: hidden` so the author knows; GEN-09 answers 404 when anyone but the author reports it, or one of its comments, like a draft. Comments (BLG-05) and likes (BLG-06) answer 404 too: commenting, liking and unliking a hidden post are refused for everyone but its author, and the comment list (a public route, which does not know who is asking) answers 404 for everyone. All of them use one filter, `visiblePublishedPost(postId, viewerId?)` in `visible-post.filter.ts`. **The public post routes (BLG-02 post page, BLG-08 tag lists, BLG-09 search, BLG-12 author pages) must leave out posts with `moderation: hidden`, except for the author.** Admins read any post, hidden or not, through `GET /api/admin/content/post/:id` (`PostsService.findForAdmin`). Add `moderation: { $ne: 'hidden' }` to their filter, or reuse `visiblePublishedPost`. The tag page (BLG-08), the search and the newest list (BLG-09) do it through `PublishedPostsService.publishedFilter()` (see "Post tags" and "Search posts" below), and the other public lists start from the same filter.
- **Methods for the admin module (GEN-10)**, never used by a controller: `findForAdmin(id)` (any post, draft or hidden too, and whether it is hidden, for `GET /api/admin/content/post/:id`), `existsById`, `setHidden(id, hidden)` (one conditional update that answers `false` when nothing changed, so the admin route can answer 404 or 409) and `removeByAdmin(id)` (deletes any post and returns its image file names; the admin module deletes the files with `UploadsService.deleteImage`). `removeByAdmin` also deletes the post's comments and likes through `removeEngagementOfPost(postId)`, which deletes the comments and likes of that one post (`postId` filter, never a broad set). BLG-04's own post delete (`remove`) calls the same method, so no comments or likes are left pointing at a deleted post. If that cleanup fails after the post is deleted, `removeByAdmin` logs it instead of answering 500 (a retry would answer 404 and the images would never be removed).
- Titles and bodies are trimmed and validated before persistence. A title has at most 200 characters and a body at most 20,000 (`POST_TITLE_MAX_LENGTH`, `POST_BODY_MAX_LENGTH` in `create-post.dto.ts`), in the DTO and in the schema. The workbook sets no limit; these keep one request from storing megabytes of text.
- Moments in the response (`createdAt`, `updatedAt`, `publishedAt`) are UTC ISO strings ending in `Z`, made by the mapper. A draft has no `publishedAt`, so it is left out.
- Tags are optional, limited to five tags, limited to 30 characters each, normalized to lowercase, trimmed, and deduplicated.
- Post images are stored as uploaded file names (`images`). Creating a post takes no images: they are added afterwards with `POST /api/posts/:id/images` (BLG-10), under the shared upload rules (GEN-08).
- API responses use a mapper and response DTO rather than exposing the Mongoose document directly.
- Creating posts is restricted to authenticated registered users with the `User` role.
- `PostsService.findPublishedSummary(postId)` (GEN-09, GEN-10) is used by the reports module: it returns the author id and the moderation of a published post, or `null` for a missing post or a draft, so a draft is never revealed. Reports leave a hidden post out for everyone but its author. No controller exposes it. When posts get an author-deactivated field (ACC-12), it must return that too.

## Editing and deleting posts (BLG-04)

- `PATCH /api/posts/:id` and `DELETE /api/posts/:id` are for registered users (`user` role) and only for the post's own author. A missing post answers 404, someone else's post 403, a malformed id 400.
- An author may change the `title`, `body`, `status` and, since BLG-08, the `tags`. Images (BLG-10) have their own routes, and a body with any other field answers 400.
- Publishing sets `publishedAt` if the post has none. Editing a published post keeps its `publishedAt`. Changing a published post back to `draft` clears it. A field sent as `null` answers 400, and an empty body changes nothing.
- `DELETE /api/posts/:id` answers 204 with no body.
- Deleting a post also deletes its comments and likes (`removeEngagementOfPost`), so none are left pointing at it. The post is deleted first; if the cleanup then fails, the error is logged and the request still answers 204.
- The author's delete does not delete image files yet. The admin delete (GEN-10) already does. BLG-10 (post images) adds this to the author's delete when posts can have images.

## Post tags (BLG-08)

- **Adding tags at creation already worked (BLG-01).** The rules now live in one place, `PostTags()` in `dto/post-tags.decorator.ts`, used by `CreatePostDto` and `UpdatePostDto`: trimmed, lowercased, de-duplicated, empty ones dropped, at most 5 of at most 30 characters (`POST_TAGS_MAX_COUNT`, `POST_TAG_MAX_LENGTH` in `blog.constants.ts`). Creating a post behaves exactly as before.
- **Editing tags.** `PATCH /api/posts/:id` takes an optional `tags`. The list sent replaces the old one, `[]` removes them all, leaving it out keeps them, and `null` is 400. The owner rules of BLG-04 apply (403 for another user, 404 for a missing post).
- **The tag page.** `GET /api/tags/:tag/posts` is public. The tag is read like a saved tag (trimmed and lowercased); an empty one or one over 30 characters is 400. It lists the **published** posts that have the tag, newest first (`publishedAt`, then `_id`), 10 per page by default (GEN-05). A tag nobody uses gives an empty page, not 404.
- **One row shape for public lists.** `PostSummaryResponseDto` (`toPostSummary`): `id`, `title`, `author: { id, name }`, `publishedAt`, `excerpt`, `tags`, `likeCount`, `commentCount`. The search (BLG-09) uses it too. The excerpt is the first 200 characters of the body (`POST_EXCERPT_LENGTH`), with line breaks and runs of spaces made one space, cut at the last space before the limit (a word that ends exactly at the limit is kept, and one long word is cut without splitting an emoji), plus "…" when something was cut.
- **Author names come from `users`, never from the post.** `PublishedPostsService` reads the names of the authors of a page in one query by their ids, selecting only `name`. `BlogModule` imports `UsersModule`, which exports the `User` model, as the admin, flights and hotels modules do; the users module is not changed. An author whose account is gone or deactivated is shown as "Deleted user".
- **One place says what the public may see.** Every public list starts from `PublishedPostsService.publishedFilter()`: `status: published` and `moderation: { $ne: 'hidden' }`, so a post stored before `moderation` existed still counts as visible.
- **The tag page leaves out hidden posts (GEN-10).** A post an admin has hidden is missing from `GET /api/tags/:tag/posts` and from its `total`, for everyone: the route is public and does not know who is asking, so its author does not see it there either (they still see it in "my posts", BLG-03). When the admin shows it again, it is listed again.
- **Posts of deactivated authors are left to ACC-12.** Until ACC-12, a deactivated author's published posts still show, under "Deleted user". The data model says `authorDeactivated` hides the post, so ACC-12 adds that condition to `publishedFilter()` and changes the matching case of `test/blog-tags.e2e-spec.ts` on purpose.
- **Index:** (`tags`, `status`, `moderation`, `publishedAt`, `_id`) for the tag page. The tag and the two filter fields come first and the newest-first sort keys last, so the whole query of the tag page runs on the index.
- **Tests:** `dto/update-post.dto.spec.ts` (tag cases), `posts.service.spec.ts`, `mappers/post-summary.mapper.spec.ts`, `published-posts.service.spec.ts` (with `publishedFilter`), `models/blog-post.schema.spec.ts` (the index), `tags.controller.spec.ts` and `test/blog-tags.e2e-spec.ts` (with hide and show again). In `test/blog-edit-delete-post.e2e-spec.ts`, the case that refused `tags` on PATCH now refuses `images`, which still have their own routes.

## Search posts (BLG-09)

- **`GET /api/posts` is public.** With `q`, it searches; without `q`, it lists the newest published posts. That feed is the minimal browse that BLG-02 extends later on the same route. The route is in its own `PostSearchController` (`@Controller('posts')`), so `PostsController` is unchanged and `GET /api/posts/mine` keeps its own path.
- **Query.** `SearchPostsQueryDto` extends `PaginationQueryDto` with an optional `q`, trimmed, 1 to 100 characters (`POST_SEARCH_MAX_LENGTH`; the workbook sets no limit). An empty or spaces-only `q` is 400: leave it out to list everything. Unknown parameters are 400.
- **What matches.** A post matches when the keyword is in its title, in one of its tags, or in the name of its author, ignoring letter case; part of a word is enough. The keyword is escaped (`search-pattern.ts`), so characters such as `.*(` are plain text and can neither fail nor match everything. Authors are found first, by name, among active registered users, then their posts by id, so no name is copied into the posts. At most 500 matching authors are read (`SEARCH_AUTHORS_MAX_COUNT`, in a fixed order by id), which keeps one `$in` list bounded: a very short keyword that matches more names than that misses the posts of the other authors (it still finds them by title and tag). A keyword with a control character, such as a null byte, is 400, because MongoDB refuses such a pattern.
- **Only published posts that an admin has not hidden (GEN-10)**, through the same `publishedFilter()` as the tag page. The search and the newest list both start from it, so a hidden post is not found by its title, its tags or its author's name, is not in the newest list, and is not counted in `meta.total`, for everyone (the route is public and does not know who is asking). When an admin shows it again, it is back.
- **Order.** Interaction score (likes + comments) descending, then `publishedAt` descending, then `_id`, so a page never shifts between two reads. The score is computed in an aggregation (`$match`, `$addFields`, `$sort`, `$skip`, `$limit`, `$project`); the total is a separate count with the same filter. Pages follow GEN-05.
- **Indexes.** A keyword is matched anywhere in the text, ignoring case, so no index can serve it: every search reads the published posts. That is fine at this project's size. The feed without `q` uses the `publishedAt` index.
- **No results** is an empty page (`items: []`, `meta.total: 0`); the frontend shows "no results".
- **Rows** are `PostSummaryResponseDto` (BLG-08): title, author, date and excerpt as the requirement asks, plus tags and the two counters.
- **Tests:** `search-pattern.spec.ts`, `dto/search-posts-query.dto.spec.ts`, `post-search.controller.spec.ts`, the search and newest-list cases of `published-posts.service.spec.ts` (with the moderation condition), and `test/blog-search.e2e-spec.ts` (with hide and show again: by title, tag and author name, in the newest list and in `meta.total`).

## Post images (BLG-10)

- **Two routes, for the author only.** `POST /api/posts/:id/images` adds images and `DELETE /api/posts/:id/images/:imageId` removes one. Both are `@Roles(Role.User)`; the service then checks that the caller wrote the post (404 for a missing post, 403 for someone else's). Drafts and published posts both take images. They live in `PostImagesController` and `PostImagesService`, so `PostsController` is unchanged. `BlogModule` imports `UploadsModule`.
- **The shared upload rules (GEN-08).** `@UploadImages()` reads the multipart field `images`. `UploadsService` refuses a file over 5 MB (413), a file that is not a JPG or PNG by its first bytes (415) and a request with no file (400). `assertWithinLimit('post', existing, incoming)` refuses more than 5 images in all (400) before anything is saved.
- **The limit holds under concurrent uploads.** After saving, the names are added with one conditional update whose filter matches only while the post still has room for all of them (`images.<5 - incoming>` must not exist). Two uploads at the same time can therefore never pass 5: the one that loses gets 400 with the limit message (without the "It already has" count when it lost at the update). Hotel photos (HTL-01) use a stricter filter (the count must be unchanged, 409 otherwise); here an upload that still fits succeeds even if another one landed first.
- **No orphan files.** When the conditional update does not match, or anything fails after saving, the files just saved are deleted again. Every file is tried; one that cannot be deleted is logged, and the caller still gets the original error, not a 500 from the cleanup.
- **`imageId` is the stored file name**, as in the hotel photos route and as `BlogPost.images` stores it. Removing pulls the name in one update (404 when the post has no such image, and then no file is touched) and then deletes the file.
- **The answer is the post** (`PostResponseDto`, 200), as the hotel photo routes answer with the hotel. `images` lists the file names; each is served at `/api/uploads/<name>`.
- **Deleting a post must delete its image files too.** The admin delete (GEN-10) already does. The author's delete (`PostsService.remove`, BLG-04) does not yet, so a deleted post leaves its image files on disk.
- **Tests:** `post-images.service.spec.ts` (limit, conditional-update miss, cleanup, delete), `post-images.controller.spec.ts` (roles) and `test/blog-images.e2e-spec.ts` (uploads, limits, file types, sizes, roles, two uploads at once, removal and the file on disk).

## Comments (BLG-05)

- Comments are stored in their own `comments` collection (`Comment` schema), not inside the post, because a post can have any number of them.
- `POST /api/posts/:id/comments` is for registered users (`user` role). The author is the logged-in user and the post comes from the route; the body carries only the text.
- The text is trimmed, must not be empty and has at most 500 characters (`COMMENT_BODY_MAX` in `blog.constants.ts`). A comment of spaces only is rejected.
- Only a published post can be commented on. A draft answers 404, the same as a missing post, so nobody can tell that a draft exists.
- `GET /api/posts/:id/comments` is public and paginated. It returns the comments oldest first (`createdAt`, then `_id` as a tie-breaker), which is the chronological order BLG-05 asks for. The endpoint table of the project description has no route for reading comments, so this one was added; the post page (BLG-02) can call `CommentsService.listForPost` instead.
- The post keeps a `commentCount`, as in the data model of the spec. **It is the number of the post's visible comments**: a new comment +1, an admin hiding one -1, showing it again +1, deleting a visible comment -1, deleting a hidden one 0 (it was already taken off when it was hidden), the author's own delete (BLG-07) included. Each change is one `$inc` update that runs only after the comment really changed state (a conditional update or a `findOneAndDelete` that returns the comment), so two requests at the same moment cannot count twice, and every decrement is guarded with `commentCount: { $gt: 0 }`, so it never goes below 0. It is not part of `PostResponseDto` yet; BLG-02 adds it to the post page.
- Index: (`postId`, `createdAt`) for the list.

## Comment moderation (GEN-10)

- A comment has `moderation`: `visible` (the default) or `hidden` (`CommentModeration`, with an explicit `type: String` in `@Prop`). Only an admin changes it, through `PATCH /api/admin/content/comment/:id` or by resolving a report (`admin` module); no blog DTO accepts it. A comment stored before the field existed counts as visible (`$ne: 'hidden'` in the filters, `?? visible` in the mapper).
- **A hidden comment is left out of `GET /api/posts/:id/comments` for everyone**, the total included: the route is public, so it does not know who is asking. Its author can still edit or delete it (BLG-07), and the comment's answer has `moderation`, so the author is told it is hidden.
- **Methods for other modules**, never used by a controller: `findSummary(id)` (reports, GEN-09: author, post and moderation, or `null`), and for the admin module `findForAdmin(id)` (the comment, hidden or not, for `GET /api/admin/content/comment/:id`), `existsById`, `setHidden(id, hidden)` (one conditional update that answers `false` when nothing changed, and moves `commentCount`) and `removeByAdmin(id)` (deletes exactly one comment by id and lowers `commentCount` if it was visible). `PostsService.isVisibleTo(postId, viewerId)` tells reports whether the post of a comment may be seen, by `visiblePublishedPost`.

## Likes (BLG-06)

- Likes are stored in their own `likes` collection (`Like` schema): one document per user and post.
- "Like once" is enforced by the unique (`postId`, `userId`) index, not by a read before the write. Two requests at the same moment cannot store two likes; the second answers 409 "You have already liked this post".
- `POST /api/posts/:id/like` and `DELETE /api/posts/:id/like` are for registered users (`user` role) and take no body. The user is the logged-in user. An author may like their own post; the workbook does not forbid it.
- Removing a like that does not exist answers 409 "You have not liked this post". 404 is kept for "no published post has this id", so the two cases cannot be confused.
- Only a published post can be liked. A draft answers 404, the same as a missing post.
- The post keeps a `likeCount`, as in the data model of the spec. It changes with one `$inc` update only after the like was really stored or deleted, and the decrement is guarded so the counter never goes below 0.
- Both routes return `{ postId, liked, likeCount }`, so the client can show the like count without a second request. `likeCount` is not part of `PostResponseDto` yet; BLG-02 adds it to the post page.

## Editing and deleting comments (BLG-07)

- `PATCH /api/comments/:id` and `DELETE /api/comments/:id` are for registered users (`user` role) and only for the comment's own author. The service compares the comment's `authorId` with the logged-in user: a comment of someone else answers 403, a missing comment 404.
- The author of a post cannot edit or delete other users' comments on it. Removing other people's content is moderation and belongs to the admin (GEN-10).
- `UpdateCommentDto` extends `CreateCommentDto` instead of using `PartialType`: a comment has only its text, so an edit must carry it, with the same rules (non-empty, at most 500 characters).
- An edited comment keeps its place in the list, because the list is ordered by `createdAt`. `updatedAt` shows that it was edited.
- Delete answers 204 with no body and removes exactly one record, by id, with `findOneAndDelete`. The post's `commentCount` goes down with one guarded `$inc` update only if this request really deleted the comment and the comment was visible, so two delete requests at the same moment lower it once, a hidden comment does not lower it a second time, and it never goes below 0.
