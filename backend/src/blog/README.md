# Blog Module

## Design decisions

- Blog posts are stored in the `posts` collection using the `BlogPost` Mongoose schema.
- Each post stores the authenticated user's `authorId`; the client cannot choose the author.
- `POST /api/posts` is the route of section 8 of the project description. Listing, the post page, tags and search (BLG-02, BLG-03, BLG-08, BLG-09) add their own routes and indexes.
- A post can be saved as either `draft` or `published`.
- New posts default to `draft` when no status is provided. `status` and `tags` sent as `null` answer 400 (the DTO validates them whenever they are sent, and the schema requires `status`), so no post is stored without a status.
- Published posts receive a `publishedAt` timestamp when they are created.
- `GET /api/posts/mine` (BLG-03) lists the logged-in user's own posts, drafts and published, newest first (`createdAt`, then `_id`), 10 per page by default (GEN-05). It is for the `user` role, like creating a post. The filter is the author id from the login, so nobody can see someone else's drafts. Each row (`MyPostResponseDto`) has the id, title, status, `moderation` (GEN-10), `publishedAt` (left out for a draft), `itineraryId` (BLG-13, `null` when none is attached), `createdAt`, `updatedAt`, `likeCount` and `commentCount`; the body, tags and images belong to the post page (BLG-02). Index: (`authorId`, `createdAt`, `_id`).
- The post schema has `commentCount` and `likeCount` (default 0), written exactly as in the BLG-05 and BLG-06 PRs, which keep them in step with the `comments` and `likes` collections. "My posts" only reads them. Posts are read hydrated, not with `lean()`, so the default 0 applies to posts stored before the counters existed.
- The post page `GET /api/posts/:id` (BLG-02) is in `PostPageController`, which `BlogModule` registers after `PostsController`. Routes are matched in registration order, so `GET /api/posts/mine` (BLG-03) is matched first and is never read as a post id. `test/blog-browse-open.e2e-spec.ts` and `post-page.controller.spec.ts` check it.
- **Moderation (GEN-10).** A post has `moderation`: `visible` (the default) or `hidden`. Only an admin changes it, through `PATCH /api/admin/content/post/:id` or by resolving a report (`admin` module); no blog DTO accepts it. It is separate from `status`: the author can still edit, unpublish or republish a hidden post, and it stays hidden until an admin shows it again. Posts are read hydrated in "my posts", so a post stored before the field existed reads as `visible`; `findPublishedSummary` (read with `lean()`) treats a missing value as `visible` too.
- **A hidden post is visible only to its author and to admins.** Today that means: "my posts" (BLG-03) still lists it for its author, with `moderation: hidden` so the author knows; GEN-09 answers 404 when anyone but the author reports it, or one of its comments, like a draft. Comments (BLG-05) and likes (BLG-06) answer 404 too: commenting, liking and unliking a hidden post are refused for everyone but its author, and the comment list (a public route, which does not know who is asking) answers 404 for everyone. All of them use one filter, `visiblePublishedPost(postId, viewerId?)` in `visible-post.filter.ts`. **The public post routes (BLG-02 post page, BLG-08 tag lists, BLG-09 search, BLG-12 author pages) must leave out posts with `moderation: hidden`.** They are public and do not know who is asking, so they leave the post out for its author too; the author still sees it in "my posts". Admins read any post, hidden or not, through `GET /api/admin/content/post/:id` (`PostsService.findForAdmin`). Add `moderation: { $ne: 'hidden' }` to their filter, or reuse `visiblePublishedPost`. The tag page (BLG-08), the search and the newest list (BLG-09) and the author page (BLG-12) do it through `PublishedPostsService.publishedFilter()` (see "Post tags", "Search posts" and "Author page" below), and the other public lists start from the same filter.
- **Methods for the admin module (GEN-10)**, never used by a controller: `findForAdmin(id)` (any post, draft or hidden too, and whether it is hidden, for `GET /api/admin/content/post/:id`), `existsById`, `setHidden(id, hidden)` (one conditional update that answers `false` when nothing changed, so the admin route can answer 404 or 409) and `removeByAdmin(id)` (deletes any post and returns its image file names; the admin module deletes the files with `UploadsService.deleteImage`). `removeByAdmin` also deletes the post's comments and likes through `removeEngagementOfPost(postId)`, which deletes the comments and likes of that one post (`postId` filter, never a broad set). BLG-04's own post delete (`remove`) calls the same method, so no comments or likes are left pointing at a deleted post. If that cleanup fails after the post is deleted, `removeByAdmin` logs it instead of answering 500 (a retry would answer 404 and the images would never be removed).
- Titles and bodies are trimmed and validated before persistence. A title has at most 200 characters and a body at most 20,000 (`POST_TITLE_MAX_LENGTH`, `POST_BODY_MAX_LENGTH` in `create-post.dto.ts`), in the DTO and in the schema. The workbook sets no limit; these keep one request from storing megabytes of text.
- Moments in the response (`createdAt`, `updatedAt`, `publishedAt`) are UTC ISO strings ending in `Z`, made by the mapper. A draft has no `publishedAt`, so it is left out.
- Tags are optional, limited to five tags, limited to 30 characters each, normalized to lowercase, trimmed, and deduplicated.
- Post images are stored as uploaded file names (`images`). Creating a post takes no images: they are added afterwards with `POST /api/posts/:id/images` (BLG-10), under the shared upload rules (GEN-08).
- API responses use a mapper and response DTO rather than exposing the Mongoose document directly.
- Creating posts is restricted to authenticated registered users with the `User` role.
- `PostsService.findPublishedSummary(postId)` (GEN-09, GEN-10, ACC-12) is used by the reports module: it returns the author id, the moderation and `authorDeactivated` (a missing value is `false`) of a published post, or `null` for a missing post or a draft, so a draft is never revealed. Reports leave a hidden post and a post of a deactivated author out for everyone but its author. No controller exposes it.

## Editing and deleting posts (BLG-04)

- `PATCH /api/posts/:id` and `DELETE /api/posts/:id` are for registered users (`user` role) and only for the post's own author. A missing post answers 404, someone else's post 403, a malformed id 400.
- An author may change the `title`, `body`, `status` and, since BLG-08, the `tags`. Images (BLG-10) have their own routes, and a body with any other field answers 400.
- Publishing sets `publishedAt` if the post has none. Editing a published post keeps its `publishedAt`. Changing a published post back to `draft` clears it. A field sent as `null` answers 400, and an empty body changes nothing.
- `DELETE /api/posts/:id` answers 204 with no body.
- Deleting a post also deletes its comments and likes (`removeEngagementOfPost`), so none are left pointing at it. The post is deleted first; if the cleanup then fails, the error is logged and the request still answers 204.
- Deleting a post also deletes its image files (BLG-10), as the admin delete (GEN-10) does. The post is deleted with `findByIdAndDelete`, which returns the image names it had at that moment, so an image added after the owner check is deleted too. The files are deleted after the post, its comments and its likes, with `UploadsService.deleteImage`; every file is tried, and one that cannot be deleted is logged while the request still answers 204. A post with no images deletes no file. A post someone else wrote answers 403 and keeps its files.

## Post tags (BLG-08)

- **Adding tags at creation already worked (BLG-01).** The rules now live in one place, `PostTags()` in `dto/post-tags.decorator.ts`, used by `CreatePostDto` and `UpdatePostDto`: trimmed, lowercased, de-duplicated, empty ones dropped, at most 5 of at most 30 characters (`POST_TAGS_MAX_COUNT`, `POST_TAG_MAX_LENGTH` in `blog.constants.ts`). Creating a post behaves exactly as before.
- **Editing tags.** `PATCH /api/posts/:id` takes an optional `tags`. The list sent replaces the old one, `[]` removes them all, leaving it out keeps them, and `null` is 400. The owner rules of BLG-04 apply (403 for another user, 404 for a missing post).
- **The tag page.** `GET /api/tags/:tag/posts` is public. The tag is read like a saved tag (trimmed and lowercased); an empty one or one over 30 characters is 400. It lists the **published** posts that have the tag, newest first (`publishedAt`, then `_id`), 10 per page by default (GEN-05). A tag nobody uses gives an empty page, not 404.
- **One row shape for public lists.** `PostSummaryResponseDto` (`toPostSummary`): `id`, `title`, `author: { id, name }`, `publishedAt`, `excerpt`, `tags`, `likeCount`, `commentCount`. The search (BLG-09) uses it too. The excerpt is the first 200 characters of the body (`POST_EXCERPT_LENGTH`), with line breaks and runs of spaces made one space, cut at the last space before the limit (a word that ends exactly at the limit is kept, and one long word is cut without splitting an emoji), plus "…" when something was cut.
- **Author names come from `users`, never from the post.** `PublishedPostsService` reads the names of the authors of a page in one query by their ids, selecting only `name`. `BlogModule` imports `UsersModule`, which exports the `User` model, as the admin, flights and hotels modules do; the users module is not changed. An author whose account is gone or deactivated is shown as "Deleted user".
- **One place says what the public may see.** Every public list starts from `PublishedPostsService.publishedFilter()`: `status: published`, `moderation: { $ne: 'hidden' }` and `authorDeactivated: { $ne: true }` (ACC-12), so a post stored before either field existed still counts as visible.
- **The tag page leaves out hidden posts (GEN-10).** A post an admin has hidden is missing from `GET /api/tags/:tag/posts` and from its `total`, for everyone: the route is public and does not know who is asking, so its author does not see it there either (they still see it in "my posts", BLG-03). When the admin shows it again, it is listed again.
- **Posts of deactivated authors are hidden (ACC-12).** When a user deactivates their own account, `PostsService.markAuthorDeactivated(authorId)` sets `authorDeactivated: true` on all their posts (one `updateMany` filtered by the author, `timestamps: false` so `updatedAt` stays; drafts get it too). `publishedFilter()` (every public list, the tag page, the search and the author page) and `visiblePublishedPost()` (the post page, comments, likes and reports of a comment, for every viewer, its author included) leave such a post out, so it answers 404 like a missing post. Only the auth module calls it (`AccountDeactivationService`); the field is never in a request body. A post stored without the field (before ACC-12) still shows, under "Deleted user" when its author is deactivated: that is the case `test/blog-tags.e2e-spec.ts` keeps. The field has no index of its own: every public query already narrows on the indexed fields first. Comments of a deactivated author stay, under "Deleted user".
- **Index:** (`tags`, `status`, `moderation`, `publishedAt`, `_id`) for the tag page. The tag and the two filter fields come first and the newest-first sort keys last, so the whole query of the tag page runs on the index.
- **Tests:** `dto/update-post.dto.spec.ts` (tag cases), `posts.service.spec.ts`, `mappers/post-summary.mapper.spec.ts`, `published-posts.service.spec.ts` (with `publishedFilter`), `models/blog-post.schema.spec.ts` (the index), `tags.controller.spec.ts` and `test/blog-tags.e2e-spec.ts` (with hide and show again). In `test/blog-edit-delete-post.e2e-spec.ts`, the case that refused `tags` on PATCH now refuses `images`, which still have their own routes.

## Search posts (BLG-09)

- **`GET /api/posts` is public.** With `q`, it searches; without `q`, it lists the newest published posts. That feed was the minimal browse; BLG-02 extended it on the same route with the `tag` filter (see "Browse and open posts (BLG-02)"). The route is in its own `PostSearchController` (`@Controller('posts')`), so `PostsController` is unchanged and `GET /api/posts/mine` keeps its own path.
- **Query.** `SearchPostsQueryDto` extends `PaginationQueryDto` with an optional `q`, trimmed, 1 to 100 characters (`POST_SEARCH_MAX_LENGTH`; the workbook sets no limit), and, since BLG-02, an optional `tag`. An empty or spaces-only `q` is 400: leave it out to list everything. Unknown parameters are 400.
- **What matches.** A post matches when the keyword is in its title, in one of its tags, or in the name of its author, ignoring letter case; part of a word is enough. The keyword is escaped (`search-pattern.ts`), so characters such as `.*(` are plain text and can neither fail nor match everything. Authors are found first, by name, among active registered users, then their posts by id, so no name is copied into the posts. At most 500 matching authors are read (`SEARCH_AUTHORS_MAX_COUNT`, in a fixed order by id), which keeps one `$in` list bounded: a very short keyword that matches more names than that misses the posts of the other authors (it still finds them by title and tag). A keyword with a control character, such as a null byte, is 400, because MongoDB refuses such a pattern.
- **Only published posts that an admin has not hidden (GEN-10)**, through the same `publishedFilter()` as the tag page. The search and the newest list both start from it, so a hidden post is not found by its title, its tags or its author's name, is not in the newest list, and is not counted in `meta.total`, for everyone (the route is public and does not know who is asking). When an admin shows it again, it is back.
- **Order.** Interaction score (likes + comments) descending, then `publishedAt` descending, then `_id`, so a page never shifts between two reads. The score is computed in an aggregation (`$match`, `$addFields`, `$sort`, `$skip`, `$limit`, `$project`); the total is a separate count with the same filter. Pages follow GEN-05.
- **Indexes.** A keyword is matched anywhere in the text, ignoring case, so no index can serve it: every search reads the published posts. That is fine at this project's size. The feed without `q` uses the `publishedAt` index.
- **No results** is an empty page (`items: []`, `meta.total: 0`); the frontend shows "no results".
- **Rows** are `PostSummaryResponseDto` (BLG-08): title, author, date and excerpt as the requirement asks, plus tags and the two counters.
- **Tests:** `search-pattern.spec.ts`, `dto/search-posts-query.dto.spec.ts`, `post-search.controller.spec.ts`, the search and newest-list cases of `published-posts.service.spec.ts` (with the moderation condition), and `test/blog-search.e2e-spec.ts` (with hide and show again: by title, tag and author name, in the newest list and in `meta.total`).

## Browse and open posts (BLG-02)

BLG-02 adds exactly two things to what BLG-08, BLG-09 and BLG-05 already built: the `tag` filter of `GET /api/posts` and the post page `GET /api/posts/:id`. Both are public.

### Browse by tag: `GET /api/posts?tag=...`

- **`tag` is read like a saved tag, and like the `:tag` of `GET /api/tags/:tag/posts`:** trimmed and lowercased, at most 30 characters (`POST_TAG_MAX_LENGTH`, the same constant). An empty or spaces-only `tag` is 400 "tag must not be empty: leave it out to list all posts", like `q`. Without `tag` nothing changes.
- **Without `q`:** the newest published posts that have the tag (`PublishedPostsService.listNewest(query, tag)`). **With `q`:** the search of BLG-09 limited to the tag (`search(keyword, query, tag)`): `tags: tag` is added to the `$match` next to the keyword `$or`, so both must hold. The order of the search (score, then newest) does not change.
- **A tag nobody uses is an empty page** (`items: []`, `meta.total: 0`), not 404, as on the tag page.
- **Same posts as the tag page.** `GET /api/tags/:tag/posts` (BLG-08) is unchanged. For the same tag and page, it and `GET /api/posts?tag=` return exactly the same `items` and `meta`; the e2e test compares them for several pages. Both go through `listNewestMatching`, which starts from `publishedFilter()`, so a draft or a hidden post (GEN-10) is never listed and never counted.
- **No new index.** The (`tags`, `status`, `moderation`, `publishedAt`, `_id`) index of the tag page serves the filter. With `q` the keyword is still matched anywhere in the text (see "Search posts"); the tag only narrows what is read.

### The post page: `GET /api/posts/:id`

- **Public and without a lock in Swagger.** `PostPageController` (`@Controller('posts')`) only handles HTTP and `PostPageService.findPage` holds the logic. It is registered after `PostsController`, so `GET /api/posts/mine` is matched first (see "Design decisions").
- **Order of the checks.** (1) The id must be 24 hexadecimal characters (`ParseObjectIdPipe`), else 400. (2) The query is validated by the global pipe: `commentsPage` and `commentsLimit`, and anything else is 400. (3) The post and the first page of its comments are read at the same time. (4) If no post matches, the answer is 404 "Post not found", whatever the comments read found. (5) The names of the post author and of the authors of the comments on the page are read in one query. (6) The mapper builds the answer.
- **Only a published post that an admin has not hidden.** The post is read with `visiblePublishedPost(id)` and no viewer, as the README says for public routes. A draft, a hidden post and a post that does not exist all answer the same 404 "Post not found" (the message of the comment routes), so nobody learns that a draft exists. The author gets the same 404 for their own draft or hidden post: the route is public and does not know who is asking.
- **The page embeds the first page of the comments.** The requirement says the page shows the comments, and one request is enough to draw the page. `commentsPage` and `commentsLimit` choose another page (10 by default, at most 50: GEN-05, same rules as `PaginationQueryDto`, with names of their own because the route has no list of its own). The plain `page` and `limit` are not parameters here and are 400. Further pages can also come from `GET /api/posts/:id/comments`.
- **Comments are the same as on the comment route:** oldest first (`createdAt`, then `_id`), and a comment an admin hid (GEN-10) is left out and not counted. `CommentsService.listForPost` and the post page both call `CommentsService.findVisibleComments`, the one place with the filter, the order and the count. `listForPost` checks the post first; the page has read the post itself, so it does not check it a second time.
- **Author names in one place.** `PublishedPostsService.authorNamesOf(authorIds)` returns a map from author id to name for the active authors. The lists use it for their rows; the page uses it for the post author and the comment authors in one query. An author who is gone or deactivated is not in the map, and the mapper shows "Deleted user", as in the lists. A deactivated author's comments stay visible under that name; their posts are hidden (ACC-12, see "Posts of deactivated authors are hidden").
- **The answer** (`PostPageResponseDto`, built by `toPostPage` from an explicit list of fields): `id`, `title`, `author: { id, name }`, `publishedAt` (UTC ISO, ending in `Z`), `body` (the whole body), `tags`, `images`, `likeCount`, `commentCount`, `itinerary` (BLG-13: a summary of the attached itinerary, or `null`) and `comments: { items, meta }`. Each comment is `id`, `author: { id, name }`, `body`, `createdAt` and `updatedAt`. `images` are the stored file names; each one is served at `/api/uploads/<filename>` (GEN-08).
- **What the page leaves out, and why.** The post's `status` (only published posts have a page), `moderation` (a hidden post has no page), `authorId` outside `author`, `createdAt` and `updatedAt` of the post (`publishedAt` is the date to show), and anything about the viewer, such as "did I like it": the route is public and gives every caller the same answer. A comment has no `postId`, `moderation` or `authorId` outside `author`. Because the mapper names every field, nothing else of a stored post can reach the answer.
- **Counters.** The post is read with `lean()`, which applies no schema default, so `likeCount` and `commentCount` are `0` and `tags` and `images` are `[]` for a post stored before those fields existed. `commentCount` is the counter that `CommentsService` keeps; `comments.meta.total` is counted when the page is read. They are equal when nothing is hidden or in flight, and the e2e test checks it. They can differ for an instant while someone comments: the counter is raised after the comment is stored, and the page reads both at the same moment.
- **Liking, commenting and reporting need a login (ACC-10).** Those routes already exist with `@Roles(Role.User)` and are not changed. `test/guest-access.e2e-spec.ts` sends a guest to every route that is not public, `POST /api/posts/:id/like`, `POST /api/posts/:id/comments` and `POST /api/reports` among them, and expects 401, so the new suite does not repeat it.
- **Known limit, not part of this issue.** An author reads the body of their published posts on this page, but nowhere can they read the body of their own draft or hidden post: `GET /api/posts/mine` has no body, and this page answers 404. An edit screen (Milestone 2) will need a route for the owner.
- **Tests:** `dto/search-posts-query.dto.spec.ts` (tag), `dto/post-page-query.dto.spec.ts`, `published-posts.service.spec.ts` (tag in both modes, `authorNamesOf`), `comments.service.spec.ts` (`findVisibleComments`, `listForPost` unchanged), `post-page.service.spec.ts`, `mappers/post-page.mapper.spec.ts`, `post-page.controller.spec.ts` (public, route and registration order), `post-search.controller.spec.ts` and `test/blog-browse-open.e2e-spec.ts` (browse, the page, route order, Swagger).

## Author page (BLG-12)

- **`GET /api/authors/:id` is public**: guests and logged-in users get the same page. It is in its own `AuthorsController` (`@Controller('authors')`), which only handles HTTP; `AuthorsService.findPage` holds the logic. A malformed id is 400 (`ParseObjectIdPipe`).
- **Who has a page.** An account with the role `user` whose status is not `deactivated`. An unknown id, an administrator, a moderator and a deactivated author (ACC-12) all answer the same 404 "Author not found", so the page never reveals that an account exists or what it is. **A suspended author keeps their page**: suspension stops them from acting, it does not take down what they published, and the workbook does not ask to hide it.
- **The answer** (`AuthorPageResponseDto`) is `id`, `name`, `joinedAt` (the account's `createdAt`, UTC ISO ending in `Z`), `posts: { items, meta }` and `itineraries: { items, meta }`. It is built by `toAuthorPage` from an explicit list of fields, so the email, phone, role, status, preferred currency and password data can never reach it; the account is read with `.select('name createdAt')` too.
- **Posts**: `PublishedPostsService.listByAuthor`, which is `publishedFilter()` plus the `authorId`, so drafts, hidden posts (GEN-10) and posts of a deactivated author (ACC-12) are left out. Newest first (`publishedAt`, then `_id`). The rows are `PostSummaryResponseDto`, the same as the tag page and the search. Index: (`authorId`, `status`, `moderation`, `publishedAt`, `_id`), so the whole query runs on the index.
- **Itineraries**: `PublicItinerariesService.listByAuthor` from the itineraries module (ITN-21): public, not hidden and the author not deactivated (`PUBLICLY_VISIBLE`), most recently updated first, the same rows as the public itinerary search (no days). An itinerary made private leaves the page at once (ITN-20). `BlogModule` imports `ItinerariesModule`, which exports that service; `ItinerariesModule` does not import `BlogModule`, so there is no cycle.
- **Two lists, two pages (GEN-05).** `AuthorPageQueryDto` has `postsPage`, `postsLimit`, `itinerariesPage` and `itinerariesLimit`: pages start at 1, page sizes are 1 to 50, 10 by default. One request can page either list without moving the other. Unknown parameters are 400. An empty list is `items: []` with `total: 0` (GEN-04).
- **Swagger** shows both nested lists with their item types (`AuthorPostsPageResponseDto`, `AuthorItinerariesPageResponseDto`), the answers 200, 400 and 404, and no lock.
- **Tests:** `authors.service.spec.ts`, `authors.controller.spec.ts`, `dto/author-page-query.dto.spec.ts`, `mappers/author-page.mapper.spec.ts`, the `listByAuthor` cases of `published-posts.service.spec.ts`, `models/blog-post.schema.spec.ts` (the index) and `test/blog-author-page.e2e-spec.ts`.

## Post images (BLG-10)

- **Two routes, for the author only.** `POST /api/posts/:id/images` adds images and `DELETE /api/posts/:id/images/:imageId` removes one. Both are `@Roles(Role.User)`; the service then checks that the caller wrote the post (404 for a missing post, 403 for someone else's). Drafts and published posts both take images. They live in `PostImagesController` and `PostImagesService`, so `PostsController` is unchanged. `BlogModule` imports `UploadsModule`.
- **The shared upload rules (GEN-08).** `@UploadImages()` reads the multipart field `images`. `UploadsService` refuses a file over 5 MB (413), a file that is not a JPG or PNG by its first bytes (415) and a request with no file (400). `assertWithinLimit('post', existing, incoming)` refuses more than 5 images in all (400) before anything is saved.
- **The limit holds under concurrent uploads.** After saving, the names are added with one conditional update whose filter matches only while the post still has room for all of them (`images.<5 - incoming>` must not exist). Two uploads at the same time can therefore never pass 5: the one that loses gets 400 with the limit message (without the "It already has" count when it lost at the update). Hotel photos (HTL-01) use a stricter filter (the count must be unchanged, 409 otherwise); here an upload that still fits succeeds even if another one landed first.
- **No orphan files.** When the conditional update does not match, or anything fails after saving, the files just saved are deleted again. Every file is tried; one that cannot be deleted is logged, and the caller still gets the original error, not a 500 from the cleanup.
- **`imageId` is the stored file name**, as in the hotel photos route and as `BlogPost.images` stores it. Removing pulls the name in one update (404 when the post has no such image, and then no file is touched) and then deletes the file.
- **The answer is the post** (`PostResponseDto`, 200), as the hotel photo routes answer with the hotel. `images` lists the file names; each is served at `/api/uploads/<name>`.
- **Deleting a post deletes its image files too**, the author's delete (`PostsService.remove`, BLG-04, see above) as well as the admin delete (GEN-10), so no deleted post leaves files on disk. `PostsService` takes `UploadsService` for this; the controllers stay HTTP only.
- **Tests:** `post-images.service.spec.ts` (limit, conditional-update miss, cleanup, delete), `post-images.controller.spec.ts` (roles), `posts.service.spec.ts` (the files of a deleted post: the names reach `deleteImage`, a file that cannot be deleted is logged and the delete still resolves, no images means no call) and `test/blog-images.e2e-spec.ts` (uploads, limits, file types, sizes, roles, two uploads at once, removal and the file on disk, and deleting the post: 204 and both files answer 404, while another user's delete answers 403 and the files stay).

## Comments (BLG-05)

- Comments are stored in their own `comments` collection (`Comment` schema), not inside the post, because a post can have any number of them.
- `POST /api/posts/:id/comments` is for registered users (`user` role). The author is the logged-in user and the post comes from the route; the body carries only the text.
- The text is trimmed, must not be empty and has at most 500 characters (`COMMENT_BODY_MAX` in `blog.constants.ts`). A comment of spaces only is rejected.
- Only a published post can be commented on. A draft answers 404, the same as a missing post, so nobody can tell that a draft exists.
- `GET /api/posts/:id/comments` is public and paginated. It returns the comments oldest first (`createdAt`, then `_id` as a tie-breaker), which is the chronological order BLG-05 asks for. The endpoint table of the project description has no route for reading comments, so this one was added; the post page (BLG-02) embeds the first page of the same list, read by `CommentsService.findVisibleComments`, the method that `listForPost` uses too.
- The post keeps a `commentCount`, as in the data model of the spec. **It is the number of the post's visible comments**: a new comment +1, an admin hiding one -1, showing it again +1, deleting a visible comment -1, deleting a hidden one 0 (it was already taken off when it was hidden), the author's own delete (BLG-07) included. Each change is one `$inc` update that runs only after the comment really changed state (a conditional update or a `findOneAndDelete` that returns the comment), so two requests at the same moment cannot count twice, and every decrement is guarded with `commentCount: { $gt: 0 }`, so it never goes below 0. It is not part of `PostResponseDto`; the post page (BLG-02) shows it as `commentCount`.
- Index: (`postId`, `createdAt`) for the list.

## Comment moderation (GEN-10)

- A comment has `moderation`: `visible` (the default) or `hidden` (`CommentModeration`, with an explicit `type: String` in `@Prop`). Only an admin changes it, through `PATCH /api/admin/content/comment/:id` or by resolving a report (`admin` module); no blog DTO accepts it. A comment stored before the field existed counts as visible (`$ne: 'hidden'` in the filters, `?? visible` in the mapper).
- **A hidden comment is left out of `GET /api/posts/:id/comments` for everyone**, the total included: the route is public, so it does not know who is asking. Its author can still edit or delete it (BLG-07), and the comment's answer has `moderation`, so the author is told it is hidden.
- **Methods for other modules**, never used by a controller: `findSummary(id)` (reports, GEN-09: author, post and moderation, or `null`), and for the admin module `findForAdmin(id)` (the comment, hidden or not, for `GET /api/admin/content/comment/:id`), `existsById`, `setHidden(id, hidden)` (one conditional update that answers `false` when nothing changed, and moves `commentCount`) and `removeByAdmin(id)` (deletes exactly one comment by id and lowers `commentCount` if it was visible). `PostsService.isVisibleTo(postId, viewerId)` tells reports whether the post of a comment may be seen, by `visiblePublishedPost`.

## Likes (BLG-06)

- Likes are stored in their own `likes` collection (`Like` schema): one document per user and post.
- "Like once" is enforced by the unique (`postId`, `userId`) index, not by a read before the write. Two requests at the same moment cannot store two likes; the second answers 409 "You have already liked this post".
- `POST /api/posts/:id/like` and `DELETE /api/posts/:id/like` are for registered users (`user` role) and take no body. The user is the logged-in user. An author may like their own post; the workbook does not forbid it.
- Removing a like that does not exist answers 409 "You have not liked this post". 404 is kept for "no published post has this id", so the two cases cannot be confused.
- Only a published post can be liked. A draft answers 404, the same as a missing post.
- The post keeps a `likeCount`, as in the data model of the spec. It changes with one `$inc` update only after the like was really stored or deleted, and the decrement is guarded so the counter never goes below 0.
- Both routes return `{ postId, liked, likeCount }`, so the client can show the like count without a second request. `likeCount` is not part of `PostResponseDto`; the post page (BLG-02) shows it.

## Editing and deleting comments (BLG-07)

- `PATCH /api/comments/:id` and `DELETE /api/comments/:id` are for registered users (`user` role) and only for the comment's own author. The service compares the comment's `authorId` with the logged-in user: a comment of someone else answers 403, a missing comment 404.
- The author of a post cannot edit or delete other users' comments on it. Removing other people's content is moderation and belongs to the admin (GEN-10).
- `UpdateCommentDto` extends `CreateCommentDto` instead of using `PartialType`: a comment has only its text, so an edit must carry it, with the same rules (non-empty, at most 500 characters).
- An edited comment keeps its place in the list, because the list is ordered by `createdAt`. `updatedAt` shows that it was edited.
- Delete answers 204 with no body and removes exactly one record, by id, with `findOneAndDelete`. The post's `commentCount` goes down with one guarded `$inc` update only if this request really deleted the comment and the comment was visible, so two delete requests at the same moment lower it once, a hidden comment does not lower it a second time, and it never goes below 0.

## Attach an itinerary to a post (BLG-13, bonus)

Approved by the team leader as a bonus; it changes no mandatory behaviour.

- **Route**: `PATCH /api/posts/:id/itinerary` (section 8, Optional), for registered users (`user` role) on their own post, draft or published. Body `AttachItineraryDto`: `{ "itineraryId": "<id>" }` attaches the itinerary (it replaces any one attached before), `{ "itineraryId": null }` removes it. The key is required: a missing key, a value that is neither an id nor `null`, or any other field answers 400, so a body that forgets the key never removes the itinerary by accident. `@ValidateIf` skips the id check for `null` only.
- **The answer** is the post (`PostResponseDto`), which now has `itineraryId` (`null` when none is attached). "My posts" (BLG-03) has it too. The post lists (tags, search, author page) do not change.
- **The order of the checks**, each answering before the next: 400 for a malformed post id (`ParseObjectIdPipe`, before the body) or for a bad body (all body errors together); 401 for a guest; 403 for an administrator or a moderator (`@Roles(Role.User)`); 404 "Post not found", then 403 for someone else's post (`findOwnedOrThrow`, as BLG-04); for an id, 404 "Itinerary not found", then 403 "You can only attach your own itineraries" (`ItinerariesService.findOwnedOrThrow`, the itineraries convention); 409 "Only a public itinerary can be attached" when the itinerary is private or hidden by an admin (GEN-10). Only the author's own itinerary can be attached, and only a public one, because other people read the post.
- **Removing is always allowed** for the author, also when the itinerary was deleted or made private since: `null` reads no itinerary.
- **Idempotent.** Attaching the itinerary already attached, or removing when none is, writes nothing and answers 200 with the post as it is (`updatedAt` does not move).
- **One conditional update.** The post is changed with one `findOneAndUpdate` by `_id` and `authorId` (`$set` or `$unset`), so it can only ever change the author's own post; a post deleted between the check and the update answers 404.
- **Stored**: an optional `itineraryId` on the post (ObjectId, ref `Itinerary`), as the data model says ("an itinerary attached to a post, a field on the post"). No index: it is only read together with its post. A post stored before BLG-13 has none and reads as "no itinerary".
- **What readers see is decided when the page is read.** `GET /api/posts/:id` (BLG-02) shows `itinerary`: `{ id, title, countries, startDate, dayCount }`, read through `PublicItinerariesService.findPublicSummary` with the same `PUBLICLY_VISIBLE` filter as the public itinerary search and view (public, not hidden by an admin, its owner not deactivated). It is `null`, with no error, when none is attached or when the itinerary is now private, hidden, deleted or its owner deactivated their account (ACC-12); the post itself stays readable. So a later change to the itinerary is respected at once, with nothing to keep in step. The summary never has the days, activities, budget, linked bookings (ITN-27) or the owner id; the full public itinerary is at `GET /api/itineraries/public/{id}`. The author name is not repeated in it: only the author's own itinerary can be attached, so the page's `author` already names its owner.
- **The summary is read in parallel** with the author names, one query (`findOne` by id with `.select`), so a page never makes more than one extra read.
- **Deactivation (ACC-12) and admin hiding (GEN-10) need no code here.** They are covered by the read-time rule above. In a real deactivation ACC-12 also hides the author's posts, so the page answers 404 anyway; the itinerary rule is tested on its own.
- **Out of this module**: the only change is `PublicItinerariesService.findPublicSummary` in the itineraries module, a read-only method with its unit test. `BlogModule` already imports `ItinerariesModule`, which exports both services this feature uses; `ItinerariesModule` does not import `BlogModule`, so there is no cycle.
- **Tests:** `dto/attach-itinerary.dto.spec.ts`, `posts.service.spec.ts` (every branch: attach, replace, remove, idempotent, 404 and 403 of the post and of the itinerary, 409 for private and hidden, a post deleted meanwhile), `posts.controller.spec.ts` (roles, Swagger), the post and post-page mapper and service specs, and `public-itineraries.service.spec.ts`. End to end: `test/blog-itinerary.e2e-spec.ts`; `blog-browse-open` and `blog-my-posts` now expect the new fields.
