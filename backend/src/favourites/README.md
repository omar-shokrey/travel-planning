# favourites

BON-02 (optional, approved by the team leader): "The system shall allow a registered user to save hotels and public itineraries to a favourites list and view it." A new module that owns the `favourites` collection (the data model says favourites are "a new collection").

## Routes

Section 8 of the project description has no favourites route. These three are the team leader's approved design for BON-02.

| Route                        | Access                                      |
| ---------------------------- | ------------------------------------------- |
| `POST /api/favourites`       | Registered users (`user` role)              |
| `GET /api/favourites`        | Registered users, their own favourites only |
| `DELETE /api/favourites/:id` | Registered users, their own favourite only  |

A guest gets 401; an administrator or a moderator gets 403 (`@Roles(Role.User)`): staff have no favourites. The owner is always the logged-in user, never the request.

## Design decisions

- **The collection.** `favourites`: `userId`, `targetType` (`hotel` or `itinerary`, an explicit string enum), `targetId` and the timestamps. A unique index on (`userId`, `targetType`, `targetId`) makes a target appear once per user; (`userId`, `createdAt` descending) serves the list. `targetId` is not a reference: the target may be deleted.
- **Only what the public can see.** A hotel must be **active** (ACC-15); an itinerary must be **public, not hidden (GEN-10) and its author not deactivated (ACC-12)**, the same `PUBLICLY_VISIBLE` rule as the public search (ITN-21). Anything else is 404 "Hotel not found" or "Itinerary not found", so a private itinerary of someone else is never confirmed to exist. The user's own private itinerary is 404 too: only public itineraries can be saved.
- **Idempotent add.** Saving a target again changes nothing: the first add answers **201**, every later one **200** with the same favourite. The save is one atomic `findOneAndUpdate` upsert on (`userId`, `targetType`, `targetId`) that returns the favourite and whether it was there already. Two adds at the same moment both reach the unique index; the one that loses reads the winner's favourite, so it answers 200 instead of a 500 and there is never a duplicate. In the rare case that the winner's favourite was removed before the loser could read it, the loser answers 404 "Favourite not found" (Swagger says so).
- **One form of the id.** The DTO accepts a hex id in either letter case; the service turns it into an `ObjectId` once, so `6740F1C2…` and `6740f1c2…` are the same target and the answer always shows the lower-case form.
- **The 200 limit** (`FAVOURITES_MAX_PER_USER`). The workbook gives none; it is an engineering limit that keeps a list and the batch reads of a page small. A new favourite past it is 409; saving one that is already in the list still answers 200, also when the same add at the same moment saved it as the last one before the limit (it is read again before the 409). Two different adds at the same moment at 199 can end at 201; that is accepted for a soft limit.
- **`available` instead of dropping.** A favourite whose target is no longer public (the hotel was deactivated, the itinerary was made private or hidden, its author deactivated, or it was deleted) stays in the list with `available: false` and no card (`hotel` and `itinerary` are `null`). The pages and `total` stay right, and the user can still remove it. It shows again with its card if the target becomes public again.
- **The cards, batch-read.** Each item has `id`, `targetType`, `targetId`, `addedAt` (UTC), `available`, and the target's public card: for a hotel its name, city, country, stars, average rating, number of ratings and the URL of its first photo (`hotel`); for an itinerary its title, author name, countries, start date and number of days (`itinerary`). The cards of a whole page are read with **one query per target type**: `HotelsService.findPublicSummaries` and `PublicItinerariesService.findPublicCards` (one aggregation that joins the author's name), both added for this module, read only and never behind a controller. A type with no favourite on the page is not queried.
- **No leak.** Never the user's id, the itinerary's owner id, the moderation flag or a hotel's `active` flag (`toFavouriteResponse` lists its fields; `FavouriteResponseDto`).
- **The list.** Newest first, `_id` descending breaking ties so pages never repeat or skip; standard pagination (10 by default, GEN-05) with `paginate()` and `@ApiPaginatedResponse`; an optional `targetType` filter. `total` is a count with the same filter.
- **Removal.** `DELETE /api/favourites/:id` takes the favourite's own id (from the list) and deletes it with the owner in the filter (`{ _id, userId }`): another user's favourite and a missing one are the same 404 "Favourite not found", and a second removal is 404.
- **Module boundaries.** `FavouritesModule` imports `HotelsModule` and `ItinerariesModule` for their exported services; neither imports this module, so there is no cycle. It is registered in `AppModule`.
- **Not here:** favourites of flights or blog posts (BON-02 names hotels and itineraries only), and a count of how many users saved a hotel.
