# flights

Owns airline profile persistence for FLT-01: the `airlines` collection, `Airline` schema, `AirlinesService`, controller, request and response DTOs, and response mapper. The implemented scope in this module is airline profile creation, retrieval, and update (FLT-01), the airline cancellation policy (FLT-09), the airline extra baggage rule (FLT-08: `PUT /api/airlines/:id/baggage-policy`), flight creation (FLT-03: the `flights` collection, `Flight` schema, `FlightsService` and `FlightsController`), the cabin categories of a flight (FLT-04: the embedded `FlightCabin` schema, `FlightCabinsService` and `FlightCabinsController`), flight search (FLT-11: `FlightSearchService` and `FlightSearchController`), and the flight status rule (FLT-30: `flight-status.ts`).

| ------------------------------------------- | -------------- | ------------------------------------------ |
| `POST /api/airlines`                        | FLT-01         | Administrator                              |
| `GET /api/airlines/:id`                     | FLT-01         | Anyone (guest)                             |
| `PATCH /api/airlines/:id`                   | FLT-01         | Airline moderator for that airline         |
| `PUT /api/airlines/:id/cancellation-policy` | FLT-09         | Airline moderator for that airline         |
| `PUT /api/airlines/:id/baggage-policy`      | FLT-04, FLT-08 | Airline moderator for that airline         |
| `POST /api/flights`                         | FLT-03, FLT-02 | Airline moderator with an assigned airline |
| `GET /api/flights/search`                   | FLT-11         | Anyone (guest)                             |
| `POST /api/flights/:id/cabins`              | FLT-04         | Airline moderator of the flight's airline  |
| `PATCH /api/flights/:id/cabins/:cabinId`    | FLT-04, FLT-05 | Airline moderator of the flight's airline  |

Creation accepts `name`, `code`, and a required multipart `logo`. Updates accept `name` and `code`, and can replace the logo; a field sent as `null` gets 400, as in the hotel edit (HTL-01). Duplicate airline codes return 409.

## Deactivated airlines (ACC-15)

- An admin deactivates or reactivates an airline through `PATCH /api/admin/providers/airline/:id/deactivate` and `/reactivate`. `AirlinesService.setActive(id, active)` writes the flag for the admin module, with one conditional update (an airline without the field counts as active). No airlines route exposes it.
- **Every feature that shows or books flights must respect the airline's `active`:** flight search (FLT-11) leaves out flights of an airline with `active: false`, and flight booking (FLT-21) refuses them. Confirmed bookings stay valid. The search does it in its query (see "Flight search (FLT-11)"); the booking does not exist yet, and this is the rule for whoever builds it.

## Design decisions

- **The airline schema owns profile persistence.** Mongoose stores profiles in the `airlines` collection, applies timestamps, defaults `active` to `true`, and enforces a unique index on `code`.
- **The service owns database access and profile rules.** It checks duplicate codes, verifies that an airline moderator is assigned to the airline being updated, and provides `findEntityOrThrow()` for internal callers that need the raw entity.
- **Controllers return response DTOs, not Mongoose documents.** `AirlineResponseDto` and `toAirlineResponse()` expose `id`, `name`, `code`, the stored logo filename, `logoUrl`, `active`, the policy fields (`cancellationTiers`, FLT-09; `extraBagPrice`, `extraBagCurrency` and `maxExtraBags`, FLT-08), `createdAt`, and `updatedAt`. The mapper converts `_id` to a string, builds `logoUrl` with the shared upload URL helper, and formats timestamps as UTC ISO strings ending in `Z`.
- **`GET /api/airlines/:id` is open to guests.** An airline's name, code, logo, active flag and policy (cancellation tiers, extra-bag rule) are public information that guests see before they book, so the route is `@Public()`. Creating and editing an airline and setting its policies still need a login, and only those routes show the lock in Swagger.
- **Route IDs use the shared `ParseObjectIdPipe`.** A malformed airline ID is rejected with 400 before the service looks up the profile.
- **The client cannot set server-controlled profile fields.** The request DTOs accept only `name` and `code`; fields such as `active` and `_id` are rejected by validation.
- **Logo files use the shared image upload service.** Airline logos are limited to one image, JPG or PNG identified from its file signature, and 5 MB per image. The profile stores the returned filename; the image is served through `/api/uploads/<filename>`. Replacing a logo removes the previous file, and a failed database write removes the newly uploaded file.
- **Tests:** `airlines.service.spec.ts` covers service behavior. `backend/test/airlines.e2e-spec.ts` covers the airline profile routes, access rules, validation, and logo lifecycle.

## Cancellation policy (FLT-09)

`PUT /api/airlines/:id/cancellation-policy` sets the cancellation tiers of an airline and returns the airline (200). Only the airline moderator assigned to that airline may call it.

- **The policy is embedded in the airline.** The airline has a `policy` sub-document (`AirlinePolicy`), as in the Flights data model, which holds `cancellationTiers: { daysBefore, refundPercent }[]`. Tiers have no `_id`. An airline starts with no tiers, and an airline stored before FLT-09 reads as having none. The extra-bag fields of the policy (`extraBagPrice`, `maxExtraBags`) are set by their own route, FLT-08 (see "Extra baggage rule (FLT-08)"). The free baggage allowance is not part of the policy: FLT-04 keeps it on each cabin of a flight (`freeBags`, `maxBagKg`, see "Flight cabins (FLT-04)").
- **`PUT` replaces the whole list.** The body is `{ "tiers": [...] }`. The tiers sent become the policy, with nothing kept from before. An empty list means "no refund at all". The write is one `findByIdAndUpdate` with `$set` on `policy.cancellationTiers`, so a reader never sees half a policy.
- **Stored highest threshold first.** The service sorts the tiers by `daysBefore`, descending, before it saves them, so whoever reads them (the airline profile, the future booking) needs no sorting.
- **Validation in the DTO.** `daysBefore` is a whole number of 0 or more, `refundPercent` a whole number from 0 to 100, and each `daysBefore` appears once in a request: a repeated one gets 400 with a message that names it. Each tier must be an object (a tier sent as a list is refused, not walked into), and a body without `tiers`, or with `tiers` that is not a list, gets only the messages that are true for it. A tier with an unknown field, or a body with one, is refused.
- **At most 20 tiers.** The workbook sets no limit. It is an engineering safeguard (`CANCELLATION_TIERS_MAX_COUNT`) that keeps a policy small enough to show and to copy into every booking.
- **Who may set it.** `@Roles(Role.AirlineModerator)`, then the service checks the moderator's `assignment` against the airline, as `update` does: a moderator of another airline gets 403, an administrator, a user and a hotel moderator get 403 from the role guard, a guest 401. A missing airline is 404 and a malformed id 400 (`ParseObjectIdPipe`). `update` and `setCancellationPolicy` share one check, `assertAssignedModerator`, so both answer 403, also for an account that no longer exists.
- **Everyone sees the policy.** `AirlineResponseDto` has `cancellationTiers` (always a list, empty by default), so `GET /api/airlines/:id` shows the policy to guests before they book, and the `PUT` returns it. The tiers are returned flat, not under a `policy` object, and so is the extra-bag rule (FLT-08): its fields were added next to the tiers, and no existing field changed.
- **The refund rule is shared with hotels.** `refundPercentFor(tiers, daysRemaining)` in `common/cancellation-tiers.ts` is one pure function used by flights (FLT-09) and hotels (HTL-10), so both refund the same way. It returns the `refundPercent` of the tier with the highest `daysBefore` that does not exceed `daysRemaining`, or 0 when no tier applies (an empty policy, fewer days than the smallest threshold, or a negative number). It reads neither the database nor the clock. The booking cancellation (FLT-26, PAY-03) computes `daysRemaining`, the whole number of days between the cancellation and the departure, and must use the tiers **copied into the booking** when it was made, as the data model says, so a later policy change never changes the refund of an existing booking.
- **Tests:** `common/cancellation-tiers.spec.ts` (the shared refund rule), `dto/update-cancellation-policy.dto.spec.ts`, the `setCancellationPolicy` cases in `airlines.service.spec.ts`, `airlines.controller.spec.ts` (roles), the mapper spec, and `test/airlines-cancellation-policy.e2e-spec.ts`.

## Extra baggage rule (FLT-08)

`PUT /api/airlines/:id/baggage-policy` sets the extra-bag rule of an airline and returns the airline (200, `AirlineResponseDto`). FLT-08: "define a price per extra bag (>0) and a maximum number of extra bags per passenger (>=0). Each extra bag has the same maximum weight as the cabin's free baggage allowance." Section 8.3 of the project description lists the route under FLT-04 and FLT-08.

- **Only the extra-bag rule.** The free baggage allowance (`freeBags`, `maxBagKg`) stays on each cabin of a flight (FLT-04), because it can differ by cabin and by flight. The route therefore carries only what is the airline's: `extraBagPrice` and `maxExtraBags`. The cancellation tiers have their own route (FLT-09).
- **The body.** `extraBagPrice`: the price of one extra bag, per passenger and per bag, a whole number of minor units of the platform currency (USD cents, PAY-04) from 1 to `EXTRA_BAG_PRICE_MAX` (1,000,000, which is 10,000 USD). `maxExtraBags`: the most extra bags one passenger may buy, a whole number from 0 to `MAX_EXTRA_BAGS_MAX` (10). Both are required, because the `PUT` replaces the rule. 0 extra bags is valid: the airline then sells no extra bag, and the price is still stored. A missing or `null` field is 400 with "<field> is required" first; text, a fraction, a number out of range and any other field (`currency`, `maxBagKg`, `cancellationTiers`, `active`, ...) are 400 in the project error shape. The workbook gives no upper limits: they are ours, engineering safeguards against a typing mistake, like the cabin limits.
- **The weight rule.** An extra bag has the same maximum weight as the free bags of the passenger's cabin: the cabin's `maxBagKg` (FLT-04). No weight is stored in the airline. The Swagger text of both fields, the DTO and the cabin response (`maxBagKg`: "for the free bags and for any extra bag") say so. This is why a cabin's `maxBagKg` is at least 1 kg even when it includes no free bag. The booking (FLT-19) reads the price and the maximum from the airline and the weight from the cabin.
- **Stored in the policy, set field by field.** `extraBagPrice` and `maxExtraBags` live in the embedded `AirlinePolicy`, next to `cancellationTiers`, as in the data model. Both have an explicit `type: Number`, the same limits as the DTO and a whole-number validator. The write is one `findByIdAndUpdate` with `$set` on `policy.extraBagPrice` and `policy.maxExtraBags` only, never on the whole `policy`, so this route and the cancellation-policy route never overwrite each other, in either order (tested). An airline with no policy yet gets one.
- **Swagger builds its texts from the constants** (`PLATFORM_CURRENCY`, `EXTRA_BAG_PRICE_MAX`, `MAX_EXTRA_BAGS_MAX`), so a changed limit cannot leave a wrong number in the documentation.
- **Who may set it.** Exactly as the cancellation policy (FLT-09): `@Roles(Role.AirlineModerator)`, then the shared `assertAssignedModerator`. A moderator of another airline gets 403 "You can only change the policy of your assigned airline"; an administrator, a user and a hotel moderator get 403 from the role guard, a guest 401. A missing airline is 404 and a malformed id 400 (`ParseObjectIdPipe`).
- **The response: flat, next to the tiers.** `AirlineResponseDto` gets three fields next to `cancellationTiers`: `extraBagPrice`, `extraBagCurrency` (always `USD`, PAY-04, because money in a response is minor units plus a currency code) and `maxExtraBags`. They are added, not moved: no existing field changed, so whoever reads the response keeps working (only lists of the exact keys, like the one in `airlines.e2e-spec.ts`, gained the new names). An airline stored before FLT-08, or one whose moderator has not set the rule yet, reads as `extraBagPrice: null` and `maxExtraBags: 0` (no extra bag is offered): the mapper does it with `??`, so no data migration is needed. `GET /api/airlines/:id` is public, so guests see the rule before they book.
- **Bookings keep their price.** A booking copies the extra bag price it was made under (data model, Flight bookings). This route changes the airline only: no booking and no flight is touched (tested: a flight document is the same before and after).
- **Tests:** `dto/update-baggage-policy.dto.spec.ts` (every boundary, missing, null, text, fractions, unknown fields), `models/airline.schema.spec.ts` (no default, the limits, the explicit type), the `setBaggagePolicy` cases in `airlines.service.spec.ts` (the exact `$set`, the 403 and 404 answers), `airlines.controller.spec.ts` (roles, the public profile), `mappers/airline.mapper.spec.ts` (flat fields, the defaults for old airlines) and `test/airline-baggage-policy.e2e-spec.ts` (every role, the 400 table with nothing stored, 0 bags, the limits, replace, both orders with the cancellation policy, an airline with no policy at all, the guest profile, a flight left unchanged, Swagger).

## Create a flight (FLT-03)

`POST /api/flights` creates a flight of the moderator's airline and returns it (201, `FlightResponseDto`). The body is `flightNumber`, `departureAirport`, `arrivalAirport`, `departureLocal` and `arrivalLocal`; nothing else is accepted.

- **The airline comes from the moderator's assignment.** `@Roles(Role.AirlineModerator)`, then `AirlinesService.findAssignedAirlineOrThrow(userId)` reads the airline from the user's `assignment`: an airline moderator with no assigned airline gets 403 "You are not assigned to an airline"; an administrator, a user and a hotel moderator get 403 from the role guard, a guest 401. The client never sends `airlineId` or `status`: the global `ValidationPipe` (`forbidNonWhitelisted`) refuses them, and any other unknown field, with 400.
- **A deactivated airline can still create flights.** ACC-15 only hides its flights from search and blocks booking (see "Deactivated airlines" above), so the moderator may keep the schedule up to date while the airline is inactive.
- **The flight number format is ours.** The workbook gives none: 2 to 10 letters or digits (`FLIGHT_NUMBER_PATTERN`), trimmed and uppercased first, so `ms123` and `MS123` are the same number.
- **Only airports of the airports list (FLT-02).** Both codes are read from the `airports` collection in one query (`FlightsModule` imports `ReferenceModule`, which exports the `Airport` model). An unknown code is 400 on its field, and two identical airports are 400 on `arrivalAirport`.
- **Local time in, UTC stored.** `departureLocal` and `arrivalLocal` are typed as `YYYY-MM-DDTHH:mm` (seconds optional) with no `Z` and no offset (`LOCAL_DATE_TIME_PATTERN`, hours 00 to 23, then a strict calendar check). luxon reads each one in its airport's IANA `timeZone` (`DateTime.fromISO(value, { zone })`); hours are never added or subtracted by hand.
- **A local time that does not exist is refused.** In a daylight saving change the clocks skip an hour (New York, 02:00 to 03:00), and luxon silently moves such a time forward. The service formats the converted instant back in the zone and compares it with the input; when they differ, the field gets 400 ("… does not exist in America/New_York …").
- **A local time that happens twice is accepted, always as the second occurrence.** When the clocks go back, 01:30 happens twice. luxon's own guess follows the zone's offset at the moment of the request, so the same request would be stored an hour apart in summer and in winter. The service therefore takes the later of luxon's candidates (`getPossibleOffsets()`): the second occurrence, standard time in both hemispheres (New York 01:30 on 2027-11-07 is `06:30Z`, Sydney 02:30 on 2027-04-04 is `16:30Z` the day before).
- **The arrival must be after the departure, compared in UTC.** A New York 20:00 departure arriving in Cairo at 01:00 the next day looks later on the clocks but is earlier in UTC: 400 on `arrivalLocal`. The same instant is refused too.
- **The departure must be in the future**, strictly after the current UTC moment: 400 on `departureLocal`.
- **`departureDateLocal` is the departure date at the departure airport** (`YYYY-MM-DD`, matched by the schema), not the UTC date: 01:00 in Tokyo is the day before in UTC.
- **One error shape.** The rules that do not depend on each other are all checked, and one 400 lists every broken one in the project shape `{ message: 'Validation failed', errors: [{ field, messages }] }`, in the order of the fields, with the DTO field name. A time is checked only when its airport is known. The format rules of the DTO come first: the global `ValidationPipe` answers them before the service runs, so a body with a malformed field and an unknown airport reports the malformed field, and the airport and time rules once the body is well formed.
- **A moderator whose airline was deleted gets 404** "Airline not found": `findAssignedAirlineOrThrow` reads the assigned airline with `findEntityOrThrow`. Swagger documents it.
- **The duplicate rule is the unique index.** (`airlineId`, `flightNumber`, `departureDateLocal`) is unique. The service inserts with `status: scheduled` and answers MongoDB's E11000 with 409 "A flight with this number already exists for your airline on this departure date"; any other database error is rethrown. There is no check before the insert, so two identical requests at the same moment give one 201 and one 409. The index covers every status: **a cancelled flight still holds its number on that date.** The same number on another local date is fine.
- **Response.** `FlightResponseDto` (`toFlightResponse`): `id`, `airlineId`, `flightNumber`, the two airport codes, `departureAt` and `arrivalAt` as UTC ISO strings ending in `Z`, each time at its own airport (`departureLocal`, `departureTimeZone`, `departureUtcOffset`, `arrivalLocal`, `arrivalTimeZone`, `arrivalUtcOffset`, see "Local flight times (GEN-06)"), `departureDateLocal`, `status` (the status at the moment of the request, see "Flight status (FLT-30)"), `createdAt` and `updatedAt`. `FlightStatus` is in `models/flight-status.enum.ts`. The response also has `cabins` (FLT-04), empty for a new flight: the moderator adds them afterwards (see "Flight cabins (FLT-04)").
- **Tests:** `dto/create-flight.dto.spec.ts` (each field's rule and message, missing, null and unknown fields, through the global pipe options), `models/flight.schema.spec.ts`, `flights.service.spec.ts` (fake clock: time zones, DST gap and repeated hour, UTC comparison, past, collected errors, 409, 403), `flights.controller.spec.ts`, `mappers/flight.mapper.spec.ts`, `findAssignedAirlineOrThrow` in `airlines.service.spec.ts`, and `test/flights-create.e2e-spec.ts` (its own airports, airline and users; every role, every 400, the duplicate rules and Swagger).

## Local flight times (GEN-06)

GEN-06: flight times are shown in each airport's local time zone. Every flight response gives the departure time at the departure airport and the arrival time at the arrival airport, next to the UTC moments.

- **Six fields, after `departureAt` and `arrivalAt`.**

  | Field                | Format                                       | Example            |
  | -------------------- | -------------------------------------------- | ------------------ |
  | `departureLocal`     | `YYYY-MM-DDTHH:mm`, at the departure airport | `2027-01-15T10:00` |
  | `departureTimeZone`  | IANA time zone of the departure airport      | `Africa/Cairo`     |
  | `departureUtcOffset` | `+HH:MM` or `-HH:MM` at the departure        | `+02:00`           |
  | `arrivalLocal`       | `YYYY-MM-DDTHH:mm`, at the arrival airport   | `2027-01-15T15:00` |
  | `arrivalTimeZone`    | IANA time zone of the arrival airport        | `America/New_York` |
  | `arrivalUtcOffset`   | `+HH:MM` or `-HH:MM` at the arrival          | `-05:00`           |

- **UTC is stored, local is computed on read.** The database keeps `departureAt` and `arrivalAt` in UTC only. `toLocalTime(instant, timeZone)` (`flight-local-time.ts`) converts each moment with luxon in the airport's IANA `timeZone` from the airports list (`DateTime.fromJSDate(instant, { zone })`); hours are never added or subtracted by hand. An unknown zone throws: no user input reaches it, so it means broken reference data.
- **The offset is the zone's offset at that moment**, so it follows daylight saving: New York is `-05:00` in January and `-04:00` in July. Offsets that are not whole hours come out as they are (`+05:30` Kolkata, `+05:45` Kathmandu).
- **Local uses the input format**, `YYYY-MM-DDTHH:mm` (the format of `departureLocal` and `arrivalLocal` in FLT-03), so the moderator gets back what they typed. Seconds, which the input allows, are not shown. A time that happens twice is stored as its second occurrence, as the FLT-03 section explains, so it comes back as the same wall-clock time with the standard-time offset (New York 01:30 on 2027-11-07 is `06:30Z`, shown as `01:30` and `-05:00`).
- **One place turns stored flights into responses: `FlightResponsesService`** (`flight-responses.service.ts`, exported by `FlightsModule`). `toResponse(flight, now)` maps one flight; `toResponses(flights, now)` reads the time zones of all the airports of a list in **one** query (`{ _id: { $in: codes } }`, `timeZone` only, lean), never one per flight, then maps each flight with `toFlightResponse(flight, now, zones)`, which stays pure. `timeZonesOf(codes)` is the one zone lookup: `FlightsService.create` uses it for its input conversion too, and passes the zones it read to `toFlightResponse`, so creating a flight still makes one zone query. Adding or editing a cabin (FLT-04) returns through `toResponse`.
- **No fallback zone.** If an airport of a stored flight is missing from the airports list, the service throws an error naming the code (500). It never guesses a zone and never shows UTC as if it were local.
- **The rule for later issues:** every route that returns a flight (FLT-17 details, FLT-23 e-ticket, FLT-25 my bookings, FLT-29 passenger export) uses `FlightResponsesService`, or `toLocalTime` for a single time, so local times are shown everywhere. The search (FLT-11) already does: it reads the two time zones with `timeZonesOf` (the same query that checks that the airports exist) and maps each result with `toFlightResponse`.
- **Tests:** `flight-local-time.spec.ts` (fixed instants: Cairo, New York in winter and summer, Tokyo on the next date, Kolkata, Kathmandu, the repeated New York hour, an unknown zone), `mappers/flight.mapper.spec.ts` (the six fields, the UTC fields unchanged), `flight-responses.service.spec.ts` (one query for a list of three flights with four airports, an empty list with no query, a missing zone), the GEN-06 cases of `flights.service.spec.ts` and `flight-cabins.service.spec.ts`, and `test/flights-local-times.e2e-spec.ts` (create in winter and summer, add a cabin, Swagger).

## Flight cabins (FLT-04)

`POST /api/flights/:id/cabins` adds a cabin category to a flight (201) and `PATCH /api/flights/:id/cabins/:cabinId` changes one (200, FLT-04 with the seat and price rules of FLT-05). Both answer the whole flight (`FlightResponseDto` with its `cabins`). They are in `FlightCabinsController` (HTTP only) and `FlightCabinsService`.

- **Who may call them.** `@Roles(Role.AirlineModerator)`, then `AirlinesService.findAssignedAirlineOrThrow(userId)`, as in FLT-03: an airline moderator with no airline gets 403, one whose airline was deleted 404, an administrator, a user and a hotel moderator 403 from the role guard, a guest 401. The flight must belong to the moderator's airline: another airline's flight is 403 "This flight belongs to another airline". Both ids go through `ParseObjectIdPipe` (400 for a malformed id).
- **A deactivated airline may still define cabins.** ACC-15 only hides its flights from search and blocks booking, and FLT-03 lets it create flights, so its moderator can finish the schedule while it is inactive.
- **Embedded in the flight.** `FlightCabin` is a sub-schema of `Flight` (`cabins`, default `[]`), as in the data model: the seat counters live in the flight document, so the booking (FLT-22) can reserve seats with one conditional update. Each cabin keeps its own `_id`, which is the `cabinId` of the routes. A flight stored before FLT-04 has no `cabins` field, and the mapper reads it as `[]` (`?? []`), so no data migration is needed.
- **The fixed set.** `CabinClass` (`models/cabin-class.enum.ts`): `economy`, `premium_economy`, `business`, `first`, stored as a text limited to those values. Each class at most once per flight, so a flight has at most 4 cabins. The schema also refuses a repeated class when a whole document is saved.
- **The fields.** `cabin`, `totalSeats`, `price` (of one seat), `freeBags` (free checked bags per passenger) and `maxBagKg` (maximum weight of one bag), all required: a missing or `null` field is 400 with "<field> is required" first, then the rules of the field. Every number is whole: the DTO uses `@IsInt` and the schema a whole-number validator, because `min` alone would let 1.5 seats or 12.5 cents in.
- **The limits.** The workbook only says that the seat count is a whole number above 0 and the price above 0. The upper limits are ours, named constants in `flights.constants.ts`, to keep a typing mistake (an extra zero) out of the schedule: `CABIN_SEATS_MAX` 1000 seats (the largest airliners seat about 850), `CABIN_PRICE_MAX` 100,000,000 cents (1,000,000 USD per seat), `CABIN_FREE_BAGS_MAX` 10 bags, `CABIN_BAG_WEIGHT_MAX_KG` 100 kg. `freeBags` may be 0, because some fares include no bag. `maxBagKg` must be at least 1 even when `freeBags` is 0, because an extra bag has the same maximum weight as the cabin's free allowance (FLT-08).
- **Money.** `price` is a whole number of minor units (USD cents) per seat, never a float. The currency is not stored per cabin: the platform has one currency (PAY-04), and the response adds `currency: PLATFORM_CURRENCY` (`common/constants/currency.ts`).
- **The seat counters belong to the server.** A new cabin has `bookedSeats: 0` and `heldSeats: 0`; only the booking (FLT-22) will change them. The client can never send them, nor `currency`, `availableSeats`, an `id`/`_id` or any other field: the global `ValidationPipe` (`forbidNonWhitelisted`) answers 400. The response never shows them either (internal hold fields stay inside): a cabin shows `availableSeats`, computed by the mapper as `totalSeats - bookedSeats - heldSeats`.
- **Adding a cabin is one conditional write.** `updateOne({ _id, airlineId, ...scheduledFlightFilter(now), 'cabins.cabin': { $ne: cabin } }, { $push: { cabins: newCabin } }, { runValidators: true })`. The new cabin gets a new `ObjectId` and counters at 0. "Each class once per flight", "own airline" and "scheduled" are decided by the database in the same operation, so five identical requests at the same moment give exactly one 201 and four 409 (tested). Different classes added at the same moment all succeed, because `$push` adds to the list instead of replacing it.
- **When the write matched nothing, one read tells why**, in this order: 404 "Flight not found"; 403 "This flight belongs to another airline"; 409 "Only a scheduled flight can be changed" (cancelled, departed, or its departure time has passed: `effectiveStatus`, FLT-30); 409 "This flight already has an economy cabin" (the class named by its API value, the value the client sent, for example `premium_economy`); otherwise 409 "The flight was changed by another request. Try again." (it changed between the write and the read).
- **What an edit may change.** `totalSeats`, `price`, `freeBags` and `maxBagKg`; a field that is left out keeps its value. `UpdateCabinDto` validates a field whenever it is sent (`whenSent`, as `UpdateRoomDto` in HTL-05), so `null` is 400; it is not `PartialType(CreateCabinDto)`, whose `@IsOptional()` would let `null` through. The class cannot be changed: `cabin` is not a field of the DTO, so sending it is 400. An empty body is 400 "Send at least one of totalSeats, price, freeBags or maxBagKg", checked in the service before anything is read, as in HTL-05.
- **An edit is a compare-and-set.** The service reads the flight and checks, in this order: 404 "Flight not found", 403 "This flight belongs to another airline", 409 "Only a scheduled flight can be changed" (also when the departure time has passed), 404 "Cabin not found", then the seat floor. It then writes with `updateOne({ _id, airlineId, ...scheduledFlightFilter(now), cabins: { $elemMatch: { _id: cabinId, bookedSeats, heldSeats } } }, { $set: { 'cabins.$.<field>': value } }, { runValidators: true })`, with the counters it read. If a booking moved them in between (or the flight changed), nothing matches: the service reads again, checks again and retries, up to 3 tries (`CABIN_UPDATE_ATTEMPTS`), then answers 409 "The cabin was changed by another request. Try again." A write that matches but changes no value is a success.
- **The seat floor (FLT-05).** `totalSeats` below the seats already booked or held is 400 on `totalSeats` in the project shape (`errors: [{ field: 'totalSeats', messages: ['totalSeats cannot be below the 15 seats already booked or held'] }]`). Equal is allowed: the cabin then has 0 available seats. Because the write carries the counters it was checked against, a booking at the same moment can never leave fewer seats than booked.
- **A new price applies to new bookings only (FLT-05).** A booking copies the price it was made at (see the data model), and the edit never touches bookings.
- **Why the rules are in the write itself.** A check followed by a separate write lets another request slip in between: two tabs adding the same class, a flight cancelled during the edit, a booking taking seats while the count is reduced. With the rules in the filter of one update on one document, MongoDB decides atomically, and no transaction or lock is needed.
- **Error order.** The login and role checks come first (401 for a guest, 403 for a role other than airline moderator, from the guards, before any pipe), then the id pipes and the DTO format rules (400, before the service runs), then the empty body (PATCH), then the moderator's airline (403, 404), then the checks above.
- **"Scheduled" is `scheduledFlightFilter(now)` (FLT-30).** Both writes match only a flight stored as `scheduled` whose departure is after `now`, with one `now` per request, so a flight that departs between the check and the write is never changed. A cancelled or departed flight, and a flight whose departure time has passed, are refused with 409 (see "Flight status (FLT-30)").
- **The extra bags are not part of a cabin.** The price of an extra bag and the most extra bags per passenger are the airline's rule (FLT-08, `PUT /api/airlines/:id/baggage-policy`); an extra bag weighs at most the cabin's `maxBagKg`.
- **Out of scope here:** the edit of a flight's times and airports (`PATCH /api/flights/:id`, FLT-05, its own pull request), deleting a cabin and booking (FLT-22). The search (FLT-11) reads the cabins and their counters: see "Flight search (FLT-11)".
- **Tests:** `models/flight.schema.spec.ts` (cabins start empty, own id, counters at 0, the class enum, each class once, whole numbers, every limit), `dto/create-cabin.dto.spec.ts` and `dto/update-cabin.dto.spec.ts` (each field's rule and message, missing, null and unknown fields, the server-controlled fields, through the global pipe options), `flight-cabins.service.spec.ts` (the exact write filters, the new cabin, every diagnosis and its priority, the seat floor, the retry and its limit), `flight-cabins.controller.spec.ts` (roles), `mappers/flight.mapper.spec.ts` (`availableSeats`, USD, no counters, a flight with no `cabins` field), and `test/flights-cabins.e2e-spec.ts` with `test/support/flight-fixture.ts` (its own airports, airlines and accounts on the `-test` database: every role, the 400s of each field on POST and the main ones on PATCH, the 404s, five parallel identical requests, four parallel classes, flights that are not scheduled, every edit, the seat floor with counters set in the database, the schema validators that back both writes, and Swagger).

## Flight search (FLT-11)

`GET /api/flights/search` lists the flights a guest or a user can book (200, a page of `FlightSearchResultResponseDto`). FLT-11: "search flights by selecting a departure airport, arrival airport, departure date (local date at the departure airport) and number of passengers; list Scheduled flights of active airlines on that date whose available seats (total - booked - held) are sufficient; allow the user to select a flight and cabin category to continue; or show \"no flights found\" when no match exists." It is in `FlightSearchController` (HTTP only) and `FlightSearchService`.

- **Open to everyone.** `@Public()`, with no role: a guest and a logged-in user of any role get the same answer. Swagger shows no lock on it.
- **The query.** `SearchFlightsQueryDto` extends the shared `PaginationQueryDto` (`page`, `limit`, 10 per page, GEN-05) with exactly the four criteria of FLT-11: `departureAirport` and `arrivalAirport` (trimmed, uppercased, 3 letters), `departureDate` (`YYYY-MM-DD` and a real calendar date: `2026-02-30` and `2026-13-01` are 400) and `passengers` (a whole number from 1 to `FLIGHT_SEARCH_PASSENGERS_MAX`, 9). Any other parameter is 400 (`forbidNonWhitelisted`). The Swagger parameters have no `pattern`, because Swagger UI would then refuse `cai` or lower case before sending, which the API accepts; the format is in each description. The return date, the cabin filter, price filters and sorting are FLT-12 to FLT-15: they add their fields to this DTO and their stages to the query.
- **The airports must exist and differ, with the answers of FLT-03.** The service reads both codes with `FlightResponsesService.timeZonesOf` (one query, which also gives the time zones for the answer). An unknown code is 400 "departureAirport QQQ is not in the airports list" (or `arrivalAirport`), and the same airport twice is 400 "arrivalAirport must be different from departureAirport", in the project error shape; FLT-03 and FLT-11 share these messages (`unknownAirportMessage`, `SAME_AIRPORTS_MESSAGE` in `flights.constants.ts`).
- **A page beyond any real list is 400.** The shared `PaginationQueryDto` has no upper limit on `page`, and a page whose skip is not a safe integer (`page=1e20`) would reach MongoDB as a `$skip` it refuses, a 500 on a public route. The service answers 400 on `page` ("page is too large") before any query. The limit belongs in the shared DTO, in a shared-layer pull request.
- **A sent `skip` is 400, not 500.** The server computes `skip` from `page` and `limit`. In the shared `PaginationQueryDto` it is a getter only, and class-transformer assigns a sent `?skip=5` to a subclass, which throws (500). `SearchFlightsQueryDto` keeps the shared getter (`super.skip`) and adds a setter that stores a sent value as an own field, so the global validation pipe refuses it like any parameter the search does not have: 400 "property skip should not exist", in the same answer as the other errors. Elsewhere `?skip=` is not handled the same way: the routes whose query is `PaginationQueryDto` itself ignore it (200), and the subclasses without their own `skip` (hotel search, admin lists, notifications, post search, itinerary search, room status) answer 500. The proper fix is in the shared DTO, in a shared-layer pull request.
- **The date is the local date at the departure airport.** It is compared as a string with the stored `departureDateLocal` (FLT-03 computes it with luxon in the airport's time zone), so the search needs no time zone arithmetic. A flight leaving Singapore at 20:00 UTC on the 10th is found on the 11th, its local date, and not on the 10th (tested).
- **Passengers are seats.** A flight is listed when at least one cabin has `totalSeats - bookedSeats - heldSeats >= passengers`: equal is enough, and seats booked and seats held for a payment both count. Infants under 2 occupy no seat (data model), so they are not part of this number; FLT-12 and FLT-19 count them in the booking.
- **One query, decided and paged in the database.** One aggregation:
  1. `$match` on `departureAirport`, `arrivalAirport`, `departureDateLocal` and `scheduledFlightFilter(now)` (FLT-30: stored as `scheduled` and departing after `now`), which uses the index (`departureAirport`, `arrivalAirport`, `departureDateLocal`, `status`);
  2. `$addFields` with `$filter` keeps the cabins with enough seats (`fittingCabins`): the rule compares fields of one cabin, which `$elemMatch` cannot do; a flight stored before FLT-04 has no `cabins` and reads as none (`$ifNull`);
  3. `$match` drops a flight with no fitting cabin;
  4. `$lookup` on `airlines` with `active: { $ne: false }` brings the airline (name, code, logo) and drops a flight of a deactivated airline (ACC-15); an airline without the field counts as active. The airlines of the whole page come with the same query, never one query per flight;
  5. `$facet` cuts the page (`$sort` by `departureAt`, then `_id`, `$skip`, `$limit`) and counts every match from the same stages, so `total` always counts what the pages show.

  The search only reads: no write, no lock, no counter changed (tested: the flights are the same before and after).

- **What a result shows.** The flight exactly as every flight response (`toFlightResponse`: UTC times and the six local-time fields of GEN-06, `departureDateLocal`, `status`), its `airline` (`id`, `name`, `code`, `logoUrl`), and only the cabins that fit the party, each with `id`, `cabin`, `price`, `currency`, `availableSeats`, `freeBags` and `maxBagKg`. The flight `id` and a cabin `id` are what the user selects to continue to the booking (FLT-19). The seat counters, the seat total and any internal field are never returned.
- **"No flights found" is a 200 with an empty page.** No match answers `{ items: [], meta: { total: 0, ... } }` in the project's pagination shape, never 404 and never another envelope; the frontend (Milestone 2) shows the text "no flights found". A date in the past or far ahead is not an error: it finds no flight.
- **Route order.** `GET /flights/search` is a fixed path. `FlightSearchController` is registered first in `FlightsModule`, so it is matched before any `GET /flights/:id` (FLT-17), and `flights.module.spec.ts` checks the order from the module metadata.
- **Tests:** `dto/search-flights-query.dto.spec.ts` (every parameter: required, trimming and uppercase, codes, impossible dates, passengers 0, -1, 1.5, text and the maximum, page and limit, unknown parameters), `flight-search.service.spec.ts` (the exact pipeline, the seat condition evaluated for equal, one short and one more, booked and held, the page and the total, the airport answers, no query when they fail), `mappers/flight-search.mapper.spec.ts` (exact keys, no internal field, local times, UTC strings), `flight-search.controller.spec.ts` (public, no lock, the paginated response), `flights.module.spec.ts` (the route order) and `test/flight-search.e2e-spec.ts` (its own airports, airlines and far-future dates: guests and every role, each criterion alone, the local date against the UTC date, cancelled, departed and past flights, an airline deactivated, reactivated and without the field, seats equal, one short, booked and held, only the fitting cabins, no cabins, the empty page, order and pages, no write, every 400 and Swagger).

## Flight status (FLT-30)

FLT-30: a flight is `scheduled`, `cancelled` or `departed`; it becomes departed once its departure time has passed, and only scheduled flights are searchable, editable or bookable. The rule is three pure functions in `flight-status.ts`, used by every route that reads or changes a flight.

- **The three statuses.** `scheduled` is stored when a flight is created (FLT-03). `cancelled` will be stored by the cancellation (FLT-06). `departed` is **derived** from the departure time: a flight stored as `scheduled` whose `departureAt` has passed is departed.
- **`hasDeparted(flight, now)`** is `departureAt <= now`. At the exact departure instant the flight counts as departed. FLT-03 refuses a departure that is not strictly in the future, so the two rules meet at the same instant and no moment belongs to neither.
- **`effectiveStatus(flight, now)`** is the status at `now`: `departed` for a stored `scheduled` flight that has departed, otherwise the stored status. A cancelled flight stays cancelled even after its departure time, and a stored `departed` stays departed. The mapper returns it: `toFlightResponse(flight, now)` takes `now` as a required parameter, so the mapper stays pure (no clock inside) and the typecheck stops any caller that forgets it. The services pass `new Date()`, one per request.
- **`scheduledFlightFilter(now)`** is `{ status: 'scheduled', departureAt: { $gt: now } }`: the one definition of "searchable, editable or bookable", for every query and every conditional write, now and later.
- **Decision: `departed` is derived, never written by a timer.** Reasons:
  - it is exact at the instant, where a periodic sweep would leave a gap between the departure and the next run, in which a departed flight would still be editable or bookable;
  - it needs no job: `ScheduleModule.forRoot()` is registered once in `app.module.ts` for the hold-expiry jobs (FLT-22, HTL-18), but no job is needed for flight status, and none must register the scheduler a second time;
  - it never bulk-writes the shared database (no `updateMany` over flights).

  There is therefore no `@nestjs/schedule` job, `setInterval` or cron for flight status, and the stored status of a past flight stays `scheduled`. (The data model in `specs/travel-platform.md` still says a scheduled job moves flights to `departed`; changing it is a shared-layer PR.)

- **Where it applies today: the cabin routes (FLT-04) and the search (FLT-11).** The search puts `scheduledFlightFilter(now)` in the first `$match` of its query, so a past flight still stored as `scheduled` is never listed. Both cabin writes put `scheduledFlightFilter(now)` in the filter of the same `updateOne`, so a flight that departs between the check and the write is never changed. When the write matched nothing, the diagnosis answers 409 "Only a scheduled flight can be changed" for a cancelled or departed flight and also for a flight stored as `scheduled` whose departure time has passed (`effectiveStatus`). The other checks and their order are unchanged.
- **Rules for the features that come next:**

  | Feature                | Rule                                                                                                                                                        |
  | ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | FLT-05 edit a flight   | Put `scheduledFlightFilter(now)` in the same `updateOne` that changes the flight.                                                                           |
  | FLT-06 cancel a flight | Put `scheduledFlightFilter(now)` in the same `updateOne` that sets `status: 'cancelled'`, so a departed or already cancelled flight is never cancelled.     |
  | FLT-11 search          | Done: `scheduledFlightFilter(now)` in the first `$match` of the search aggregation, plus the active-airline rule (ACC-15) in its airline `$lookup`.         |
  | FLT-17 flight details  | Show `effectiveStatus(flight, now)` (the mapper already does).                                                                                              |
  | FLT-22 book seats      | Put `scheduledFlightFilter(now)` in the same conditional seat update that reserves the seats, so a flight that departs during the booking cannot be booked. |

- **No new index.** The search (FLT-11) filters by route and local date first (`departureAirport`, `arrivalAirport`, `departureDateLocal`, `status`), which leaves few flights for the `departureAt` condition; the cabin writes go by `_id`.
- **Tests:** `flight-status.spec.ts` (a fake clock that the functions must not read: 1 ms before, exactly at and 1 ms after the departure, a cancelled flight after its departure, a stored departed flight, the filter and its agreement with `effectiveStatus` at the boundary), `mappers/flight.mapper.spec.ts` (the effective status with a fixed `now`), `flight-cabins.service.spec.ts` (the filters carry `departureAt: { $gt: now }`, 409 for a past departure stored as scheduled, before the class check) and `test/flights-status.e2e-spec.ts` (adding and editing a cabin of a future scheduled flight, of a past one still stored as scheduled, of a cancelled one and of a departed one, with nothing changed in the database after each 409, and `POST /api/flights` answering `scheduled`).

## Seat holds (FLT-22)

The booking (flight-bookings module) owns the booking; this module owns the flight document and its seat counters. `FlightSeatHoldsService` (`flight-seat-holds.service.ts`, exported by `FlightsModule`) is the only way a booking holds or releases a cabin's seats. **Only the booking modules may change `heldSeats` and `bookedSeats`**, and only through this service.

- **`hold(flightId, cabin, seats, now)` is one conditional update.** `findOneAndUpdate({ _id, ...scheduledFlightFilter(now), cabins: { $elemMatch: { cabin } }, $expr: cabinHasSeatsLeft(cabin, seats) }, { $inc: { 'cabins.$[c].heldSeats': seats } }, { arrayFilters: [{ 'c.cabin': cabin }], returnDocument: 'after' })`. `cabinHasSeatsLeft` finds the cabin with `$filter` and `$arrayElemAt` and checks `totalSeats - bookedSeats - heldSeats >= seats`. The rule and the change are applied to one document atomically, so requests at the same moment never hold more seats than exist, with no transaction. `scheduledFlightFilter(now)` in the same filter means a flight that departs or is cancelled during the booking cannot be booked (FLT-30).
- **It returns the flight as the update left it**, so the booking copies the price of the same moment the seats were taken.
- **A read before the update only chooses the answer**: 404 "Flight not found" (also for a deactivated airline, ACC-15), 409 "This flight can no longer be booked" (`effectiveStatus`), 404 "This flight has no business cabin". If the update then matches nothing, a second read answers 409 "This flight can no longer be booked" or 409 "Not enough seats left in this cabin". Nothing is held in any error case.
- **`release(flightId, cabin, seats)`** is one `updateOne` that matches only if that cabin's `heldSeats >= seats`, then adds `-seats`, so a counter never goes below 0. A mismatch is logged as a counter to recompute and never thrown.
- **The cabin edit (FLT-04) is unchanged.** Its compare-and-set matches the `bookedSeats` and `heldSeats` it read, so a hold at the same moment makes it retry, then answer 409 "The cabin was changed by another request. Try again."
- **Tests:** `flight-seat-holds.service.spec.ts` (the exact filter, update and options, every error with no update, the release guard) and `test/flight-bookings-hold.e2e-spec.ts`.
