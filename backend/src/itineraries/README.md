# Itineraries module

Owner: Ali Ghayesh (M8). Requirements: ITN-01 to ITN-26. Routes: `/api/itineraries`, `/api/activities` (with `/api/activities/:id/images`), `/api/budgets`, `/api/transport-costs`.

## Design decisions

- **One document per itinerary.** Days, activities, budget entries, transport costs and the clone source are embedded in the `itineraries` collection, as in the data model of `specs/travel-platform.md`. An itinerary has one owner, at most 60 days (ITN-05), and is always read together.
- **Nothing derived is stored.** The day number is the position in `days`, and a day's date is `startDate` plus that position. City groups and budget totals are computed when read. The only stored copy is `dayCount`, which the service keeps equal to `days.length` so that public search can filter by duration with an index (ITN-21).
- **`startDate` is a `YYYY-MM-DD` string**, never a `Date`, so no time zone can shift it.
- **Money is whole minor units plus a currency code.** Each entry keeps its own currency and is converted only when read (ITN-18).
- **Every embedded item has its own `_id`**, because the routes address them directly (`/api/activities/:id`, `/api/budgets/:id`, `/api/transport-costs/:id`).
- **Countries and cities are stored as the official ids** of the reference data (`EG`, `cairo`). The service checks that they exist in the `countries` and `cities` collections, which `ReferenceModule` exports for reading.
- **Transport `mode` is free text.** The workbook lists no fixed set of modes (ITN-16).
- **Itineraries are for registered users only.** Every ITN requirement (ITN-01 to ITN-26) has the actor "Registered User", and section 4 of the project description gives itineraries to the registered user. So `ItinerariesController`, `ActivitiesController` and `TransportCostsController` carry `@Roles(Role.User)` on the class, and in `PublicItinerariesController` only the clone route does, so the two public reads (`@Public()`) stay open to guests. An administrator or a moderator gets 403 from `RolesGuard` before any lookup or id check, even for a missing itinerary or an invalid id. Administrators reach itineraries only through the admin routes (GEN-10: `GET`, `PATCH` (hide or show) and `DELETE /api/admin/content/:type/:id`), which call `ItinerariesService` directly.
- **Enums live in `enums/`** inside this module. `ItineraryModeration` (visible or hidden, GEN-10) is local for now. If blog posts and reviews need the same values, it should move to `backend/src/common/enums/` in a shared PR.

## ITN-01: create, edit, delete

- **The owner comes from the login cookie.** `CreateItineraryDto` has no owner, visibility or day count, and the global `ValidationPipe` rejects unknown fields, so a client cannot set them.
- **Countries are checked against the `countries` collection** in the service. The DTO only checks the shape (2-letter codes, at least one, no repeats). An unknown code gives 400 and names the code.
- **Ownership is 404, then 403.** A missing itinerary gives 404. An itinerary of another user gives 403, as section 11 of the development plan asks.
- **Delete removes the document.** It leaves public search at once, and a clone is a separate document with the author's name copied into `cloneSource`, so clones are not affected. The "after confirmation" step is the frontend's dialog (Milestone 2). The image files of its activities go with it (ITN-12): the names come from the document `findOneAndDelete` returns, and a file a clone still lists is kept.
- **`PATCH` changes only the fields that are sent.** A field that is absent is left as it is; `null` answers 400 (`assertNoNullFields`), as in the hotel edit (HTL-01) and the activity and transport cost edits (ITN-10, ITN-16). The edit is saved with the version check (`saveOrConflict`), so it answers 409 instead of overwriting a change made at the same moment.
- **`findEntityOrThrow()`** is for other services (for example the admin module, GEN-10). It returns the entity and is never used by a controller.
- **Admin moderation (GEN-10)** uses `existsById`, `setHidden(id, hidden)` and `removeByAdmin(id)`, at the end of `ItinerariesService`, for the admin module only. `setHidden` changes `moderation` in one conditional update and answers `false` when nothing changed (missing, or already in that state). `removeByAdmin` deletes any itinerary and returns the activity image file names that no other itinerary uses (`unusedImageNames`, the same rule as every other delete, ITN-12): a clone keeps the image names of its source (ITN-21), so a file a clone still shows is kept. The admin module deletes those files. A hidden itinerary stays visible to its owner (`GET /api/itineraries` and `/:id` filter on the owner only, so they need no change) and is left out for everyone else by GEN-09 reports and by public search and view (ITN-21, which filters on `moderation: visible`). The owner's responses show `moderation` (`visible` or `hidden`), so the author can see that an admin hid their itinerary. Public search and public view only return visible itineraries, so there `moderation` is always `visible`.
- **`findOwnerAndVisibilityOrThrow()`** is for the reports module (GEN-09): the owner id and whether the itinerary is publicly visible, by the same `PUBLICLY_VISIBLE` rule as public search (ITN-21), so a user can report exactly the itineraries search shows them. It reads only `ownerId`, `visibility`, `moderation` and `authorDeactivated`, not the days, and answers 404 for a missing itinerary.
- **The end-to-end tests add their own country.** The test database may hold no reference data (CI starts with an empty one), so the tests insert one country with a code that no real country has (`X` plus a letter) and delete it at the end, with the users and itineraries they created.

## ITN-03: list my itineraries, open one

- **The list returns the summary only** (title, countries, start date, number of days, visibility). The days come with `GET /api/itineraries/:id`, so a list of 10 itineraries never loads up to 600 days.
- **Sorted by `updatedAt`, newest first, then by `_id`**, so two itineraries updated in the same millisecond keep a fixed order across pages. The index (`ownerId`, `updatedAt`) serves it.
- **`GET /api/itineraries/:id` is for the owner only**, public or not: 404 if missing, 403 for another user. Reading someone else's public itinerary is a different route, `GET /api/itineraries/public/:id` (ITN-21).
- **A day's number and date are computed in the mapper**: the number is the position in `days` plus 1, and the date is `startDate` plus the position, added in UTC with `luxon` so a clock change cannot shift it.

## ITN-05: add days and cities

- **A new day goes at the end.** `POST /api/itineraries/:id/days` takes a city and optional notes. The client never sends a number or a date: both follow from the position. Moving a day is ITN-08.
- **The city is checked against the `cities` collection** (400 with the unknown id). The workbook does not ask that the city belongs to one of the itinerary's countries, so that is not checked.
- **Adding a day is one conditional update**: `$push` the day and `$inc` `dayCount`, only where `dayCount` is below 60. Two requests at the same moment cannot pass the limit or leave `dayCount` different from the number of days. When the update matches nothing, the itinerary is full and the answer is 409.
- **The day routes return the whole itinerary with its days**, because one change can affect the numbers and dates of other days.
- **Editing a day changes only the fields that are sent.** Empty notes clear the notes; `null` answers 400. A day always keeps a city (ITN-09), so the city can be replaced but not removed.
- **A day id that is not in this itinerary gives 404** "Day not found".

## ITN-20: public or private

- **Visibility is a field of `PATCH /api/itineraries/:id`**, as in section 8 of the project description (that route serves ITN-01 and ITN-20). There is no separate publish route.
- **Only `UpdateItineraryDto` has `visibility`.** `CreateItineraryDto` does not, so a new itinerary is always private (ITN-01) and becomes public only by an explicit edit.
- **"Read-only to other users" is the ownership check.** Every route that changes an itinerary goes through `findOwnedOrThrow()`, so another user gets 403 on a public itinerary exactly as on a private one.
- **"Setting Private removes it immediately" needs no extra work.** Nothing is copied when an itinerary is published: public search (ITN-21) will filter on the `visibility` field, so the next search after the change no longer returns it.

## ITN-07: delete a day

- **`DELETE /api/itineraries/:id/days/:dayId` returns the itinerary with its remaining days**, because the days after the deleted one get new numbers and dates. Totals are computed when read, so they change with it. The "after confirmation" step is the app's dialog (Milestone 2).
- **One update with a version check.** The service reads the itinerary, then writes the remaining days and their count in one update that only applies if the itinerary is still at the version it read, and bumps the version. So `dayCount` always equals the number of days, a day added at the same moment is never lost, and the same day deleted twice at once gives 200 and then 404 or 409.
- **Adding a day bumps the version too (ITN-05)**, so a delete that read the itinerary before that day existed is refused instead of dropping it.
- **A change by position that loses the race answers 409** "The itinerary was changed by another request". `saveOrConflict()` turns the Mongoose `VersionError` into that answer, and the day edit (ITN-05) uses it now.
- **Everything inside the day goes with it**: its activities, budget entries and transport costs, and then the image files of those activities that no activity lists any more (ITN-12).
- **The e2e tests share `test/support/itinerary-fixture.ts`**, which adds a test country and two test cities, makes users with a live session, and deletes everything by id at the end.

## ITN-08: move a day

- **`PATCH /api/itineraries/:id/days/reorder` takes `{ dayId, position }`**: the day to move and its new day number (1 is the first day). The days in between shift by one. It returns the itinerary in the new order, since every number, date and city group can change.
- **The route is declared before `PATCH :id/days/:dayId`**, or Nest would read `reorder` as a day id.
- **A position after the last day answers 400** with the allowed range. Moving a day to where it already is changes nothing and writes nothing.
- **Same versioned write as ITN-07.** `writeDays()` replaces the days in one update that only applies at the version that was read. A move and a delete at the same moment can each apply or answer 409, but never half apply, and `dayCount` always equals the number of days. This relies on MongoDB applying a single-document update atomically.

## ITN-09: city groups

- **Every day has a city.** ITN-05 already requires `cityId` on a day and checks it against the city list; this issue relies on that.
- **`cityGroups` is part of the itinerary detail** (`GET /api/itineraries/:id` and every route that returns the itinerary with its days). Consecutive days in the same city form one group with `firstDayNumber`, `lastDayNumber`, `startDate`, `endDate`, `dayCount` and `budgetSubtotal`. A city visited twice with other days in between gives two groups.
- **Computed when read, never stored**, so adding, editing, moving (ITN-08) or deleting (ITN-07) a day regroups at once. Hotel search for a group (ITN-25) can use `startDate` and the day after `endDate` as check-in and check-out.
- **The subtotal is one amount per currency.** It adds activity costs (ITN-10), budget entries (ITN-14) and transport costs (ITN-16) of the group's days, sorted by currency code. Entries keep their own currency; one total in the user's currency comes with ITN-18. An activity without a cost adds nothing. The costs come from `dayCostLines()`, the same source as the budget summary (ITN-14), so the two always agree.

## ITN-10: activities per day

- **Routes as in section 8 of the project description**: `POST /api/itineraries/:id/days/:dayId/activities` adds one; `PATCH /api/activities/:id` and `DELETE /api/activities/:id` work by the activity's own id. All are for the owner only and return the itinerary with its days, so the day list and the city group subtotals (ITN-09) are always current.
- **`ActivitiesService` and `ActivitiesController` are separate files**, so the itinerary service does not grow with every embedded list. They reuse `findOwnedOrThrow()`, `findDayOrThrow()`, `assertCurrencySupported()` and `saveOrConflict()` from `ItinerariesService`.
- **An activity is found by its id inside the days** (`days.activities._id`): 404 if no itinerary has it, then 403 if the itinerary is not the caller's.
- **A cost and its currency go together.** The DTO refuses one without the other, and an edit that would leave only one answers 400. The currency must be supported: one of the currency codes of the seeded countries (GEN-12). A cost is whole minor units, from 0 to `MONEY_AMOUNT_MAX` (see "Money limits" under ITN-14). An activity without a cost adds nothing to the budget; its cost counts under `activities` in the budget summary (ITN-14).
- **Limits not in the workbook**: name at most 100 characters, description at most 1000, so one itinerary document stays small.
- **`null` in an edit answers 400** (`assertNoNullFields`), as the hotel edit does (HTL-01). An empty description or time removes it. A cost cannot be removed once set; setting it to 0 makes it add nothing.
- **Deleting writes a new list for the day** instead of a `$pull`, and every change goes through `saveOrConflict()`, so a change that raced with a delete or a move of a day (ITN-07, ITN-08) answers 409 instead of editing the wrong day.
- **Images are ITN-12** (see "ITN-12: activity images" below). Every activity in a response has `images`, always a list. Deleting an activity also deletes its image files that no other activity lists.

## ITN-12: activity images

- **Routes as in section 8**: `POST /api/activities/:id/images` (multipart field `images`, `@UploadImages()`) and `DELETE /api/activities/:id/images/:imageId`, where `imageId` is the stored file name. They sit in `ActivitiesController`, so its class-level `@Roles(Role.User)` applies: 401 for a guest, 403 for an administrator or a moderator, then 400 for a bad id, 404 for no such activity and 403 for someone else's. Both return the itinerary with its days, like the other activity routes. The logic is in `ActivityImagesService`, so `ActivitiesService` does not grow.
- **The shared upload rule (GEN-08)** is `UploadsService`: JPG or PNG judged by the first bytes, at most 5 MB each (413 past it, 415 for another type, before anything is saved), at most 5 per activity, and one bad file in a batch stores none of them.
- **The response** lists `images: { filename, url }[]` on every activity, the same shape as hotel photos, so the owner's view, the public view and a clone (ITN-21) and the admin view (GEN-10) all show them.
- **Adding is one conditional update.** `assertWithinLimit` checks the count that was read, then `saveImages` stores the files, then one `findOneAndUpdate` pushes the names into that one activity (`arrayFilters`) only while it has room for all of them (no element at position `5 - n`), as BLG-10 does for posts. Two uploads at the same moment can never pass 5: the one that loses the race gets 400 "An activity can have at most 5 images.", and the files it saved are deleted. The pre-check answers "An activity can have at most 5 images. It already has N.": only it knows the count. The days array is never read, changed and written back for an image.
- **Every image write bumps the version (`$inc: { __v: 1 }`).** `writeDays` (ITN-07 delete, ITN-08 move) and `saveOrConflict` (ITN-10 activity edit and delete) only write at the version they read. If an image write kept the version, a day delete, a day move or an activity delete that read the activity before the image was added would write back the old list, losing the image and leaving its file behind. With the bump, that request gets 409 instead. The same is why the names a day or activity delete reads are the current ones.
- **No orphan files after a failed upload.** If the update does not match or anything throws after the files were saved, the files just saved are deleted: every file is tried, one that cannot be deleted is logged, and the original error is answered.
- **Removing is one conditional `$pull`** on that activity, matched only while it lists that name. A name it does not list is 404 "Activity image not found", and no file is touched.
- **A file is deleted only when no activity in any itinerary lists it any more.** A clone copies the image file names of its source (ITN-21), so two activities can list the same file. `ItinerariesService.unusedImageNames()` is the one place for this rule; every delete uses it: removing an image, deleting an activity (ITN-10), a day (ITN-07) or an itinerary as its owner (ITN-01), and the admin delete (GEN-10).
- **Files leave after their owner.** The database write comes first, then the files (`deleteUnusedImageFiles`). A file that cannot be deleted is logged and never turns a finished delete into a 500. An activity, day or itinerary without images makes no query and no file call. The itinerary delete takes the names from the document `findOneAndDelete` returns, so an image added after the ownership check is not missed.
- **Accepted race: a clone made at the same instant as the last delete of a shared file.** The clone (ITN-21) copies the names it read; if the last activity listing a file is deleted (or the image removed) between that read and the clone's insert, `unusedImageNames` finds no listing, the file is deleted, and the clone shows a missing image. Closing it would need the clone to take part in the file check (for example by copying the files, or by a reference count kept in `uploads/`), which is outside this module. It needs two requests on the same images within milliseconds, one by the source's owner and one by another user, and the result is one missing picture, never a broken itinerary.

## ITN-14: budget entries and totals

- **Routes as in section 8**: `POST /api/itineraries/:id/days/:dayId/budgets` adds an entry to a day; `PATCH /api/budgets/:id` and `DELETE /api/budgets/:id` work by the entry's own id; `GET /api/itineraries/:id/budget-summary` gives the totals. All are for the owner only, behind `@Roles(Role.User)`: 401 for a guest, 403 for an administrator or a moderator, then 400 for a bad id, 404, then 403 for someone else's itinerary. The three write routes return the itinerary with its days, like activities. `BudgetsService` and `BudgetsController` are their own files and reuse `findOwnedOrThrow()`, `findDayOrThrow()`, `assertCurrencySupported()` and `saveOrConflict()`. An entry is found by its id inside the days (404, then 403).
- **An entry is a category, an amount and a currency.** The category is one of the four of the workbook: `food`, `accommodation`, `local_transport` (in-city transport) and `activities`. Intercity transport is not a category: it is the transport costs of ITN-16. The amount is whole minor units from 0 to `MONEY_AMOUNT_MAX`; the currency is required and must be supported (GEN-12). `PATCH` changes only what is sent, `null` answers 400 (`assertNoNullFields`), and an empty body changes nothing, as for activities.
- **Every day in a response lists `budgetEntries`** (`{ id, category, amount, currency }`, always a list), so the owner, the public view (ITN-21) and a clone see them. A clone copies the entries with new ids; deleting a day (ITN-07) deletes its entries.
- **The summary**: `total`, `byCategory` and `byDay`, each total as one amount per currency sorted by currency code, the same rule as the city-group subtotals (ITN-09). `byCategory` always has five lines in a fixed order, even when empty: `food`, `accommodation`, `local_transport`, `activities` (entries plus activity costs, ITN-10) and `intercity_transport` (transport costs, ITN-16), so the lines add up to the total. `byDay` lists every day in order with `dayId`, `dayNumber`, `date`, `cityId`, its total and its five lines. Deleting or moving a day changes it at once, because nothing is stored.
- **One source for every total.** `dayCostLines()` gives each cost of a day with the line it counts under; `dayCosts()` (city groups), the day totals and the summary all use it, and `totalPerCurrency()` adds them up. So the total, the sum of the days, the sum of the categories and the sum of the city-group subtotals can never disagree; a unit test checks this.
- **No conversion yet.** Converting to the user's currency is ITN-18. The summary keeps one amount per currency, and every total is a list of `{ amount, currency }`, so ITN-18 can add converted totals next to these fields without changing them.
- **Money limits (engineering limits, not workbook rules).** Before ITN-14 an amount was only `@IsInt` and `@Min(0)`, and `1e300` passes `@IsInt`, so one request could make a total lose precision or become `Infinity`. Now every amount of the module (budget entry, activity cost, transport cost) is at most `MONEY_AMOUNT_MAX` = 10,000,000,000 minor units (100,000,000.00 in a 2-decimal currency), checked by the DTO (`@Max`) and by the schema (`moneyAmount`: `min`, `max` and whole units). The worst case stays a safe integer: a MongoDB document is at most 16,777,216 bytes, and every item that carries an amount takes at least 64 bytes of it (a budget entry with an `_id`, a 4-letter category, an amount and a currency is about 74 bytes in BSON; an activity with a cost or a transport cost is more). So one itinerary holds at most 16,777,216 / 64 = 262,144 amounts, and one currency's total is at most 262,144 × 10,000,000,000 = 2,621,440,000,000,000, below `Number.MAX_SAFE_INTEGER` (9,007,199,254,740,991). ITN-18 must keep that in mind when it multiplies by an exchange rate.
- **At most `BUDGET_ENTRIES_PER_DAY_MAX` = 50 entries per day**, so one itinerary document stays small (60 days × 50 entries). Adding reads the itinerary, checks the count, then pushes the entry in one update that matches only the `__v` it read and bumps `__v`, as the day writes do (ITN-07, ITN-08). Every change to the order of the days bumps `__v` (`writeDays`, and `$push` with `$inc` for a new day), and so does every add or delete of an entry (a delete saves the new array, and Mongoose then increments `__v`), so the day is still at the position that was read and the count that was checked is still true: two adds at the same moment cannot pass 50, and a day delete or move that read the itinerary before cannot drop the new entry. A request that loses the race reads again and checks again (at most 5 times, then 409 "The itinerary was changed by another request"). A full day answers 409 "A day has at most 50 budget entries"; an e2e test sends parallel adds at the cap. The update uses the day's position, not the positional `$` operator, so it needs no array filter.

## ITN-16: transport costs

- **Routes as in section 8**: `POST /api/itineraries/:id/transport-costs` with the day in the body (`dayId`), then `PATCH` and `DELETE /api/transport-costs/:id`. Owner only; each returns the itinerary with its days.
- **The fields the workbook lists**: mode, from-city, to-city, amount, currency and day. `mode` is free text up to 50 characters (train, bus, flight...), because the workbook gives no fixed list.
- **Both cities come from the city list and must differ**, since this is intercity transport (ITN-14 calls these "intercity transport entries"). An edit that changes one city is checked against the other one it keeps.
- **A transport cost belongs to one day**, so it counts in that day's city group subtotal (ITN-09) and leaves with the day if the day is deleted (ITN-07). `PATCH` with a new `dayId` moves it to that day of the same itinerary and keeps its id.
- **Amount and currency follow the money rules**: whole minor units, from 0 to `MONEY_AMOUNT_MAX`, in a supported currency. `null` in an edit answers 400, as for activities. A transport cost counts under `intercity_transport` in the budget summary (ITN-14).
- **Same design as activities (ITN-10)**: a separate `TransportCostsService` and `TransportCostsController`, found by id inside the days (404, then 403), saved through `saveOrConflict()`.

## ITN-21: search, view and clone public itineraries

- **Routes**: `GET /api/itineraries/public/search` and `GET /api/itineraries/public/:id` are open to guests; `POST /api/itineraries/:id/clone` needs a login. The two read routes sit under `/api/itineraries/public/`, the only public part of `/api/itineraries` that `test/guest-access.e2e-spec.ts` allows. `public/search` is declared before `public/:id`, or `search` would be read as an id.
- **Publicly visible means three things**: public (ITN-20), not hidden by an admin (`moderation`, GEN-10) and the author's account not deactivated (`authorDeactivated`, ACC-12). `PUBLICLY_VISIBLE` holds this filter once for search, view and clone. Anything else answers 404, so a private itinerary is never revealed, not even that it exists.
- **The keyword (`q`)** matches part of the title, in any case, or a country (its code or part of its name) or the name of a city on any day. It is matched as plain text (`escapeRegExp`), never as a pattern a caller could abuse. The queries use the `$regex` string form (`{ $regex, $options: 'i' }`), not a RegExp object: in local runs against the Atlas test database, a RegExp with the `i` flag inside `$or` sometimes never got an answer, while the string form always did (the same as ACC-14's account search). Filters: `minDays` and `maxDays` (1 to 60) on `dayCount`, `country` (code) and `city` (city id). `minDays` above `maxDays` answers 400.
- **Results are lightweight**: the list fields of ITN-03 plus `author { id, name }`, without the days (`.select('-days')`), most recently updated first, paginated. Opening one gives the full detail (days, activities, transport costs, city groups) plus the author. An author whose account is gone shows as "Unknown author".
- **A clone is a new private itinerary of the caller** with every day, activity, budget entry and transport cost copied with new ids. It shares nothing with the original, so editing or deleting either one leaves the other alone. `clonedFrom { itineraryId, authorId, authorName }` credits the author; the name is kept at clone time, so the credit stays if the original is deleted later.
- **Cloned activities keep the same image file names.** Two activities can then list the same file, so a file is deleted only when no activity in any itinerary lists it any more (`unusedImageNames`, ITN-12).

## Admin view (GEN-10)

- **`findForAdmin(id)`**, for the admin module only, returns any itinerary with its days (`toItineraryDetailResponse`), private or hidden, and whether an admin hid it, or `null`. It serves `GET /api/admin/content/itinerary/:id`, because hidden content is visible only to its author and admins (GEN-10). No itineraries controller uses it.
