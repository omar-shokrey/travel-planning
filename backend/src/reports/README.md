# reports

Owns the `reports` collection: the `Report` schema, `ReportsService`, the request and response DTOs and the mapper. Requirement: GEN-09 (report content). Route: `POST /api/reports`. Admins list and handle reports through the `admin` module (GEN-10, `GET /api/admin/reports`), which is not part of this module yet.

## Design decisions

- **Posts and itineraries only, for now.** GEN-09 also names comments and reviews. Comments (BLG-05) are in an open PR and hotel reviews are not built, so `ReportTargetType` has only `post` and `itinerary`. A later PR adds `comment` and `review` and their visibility checks. No placeholder values were added, so the API never accepts a type it cannot check.
- **`POST /api/reports` is not in section 8 of the project description**, which lists only the admin side (`GET /api/admin/reports`). The route follows the module name and the plural-noun rule of AGENTS.md. One route for every type keeps the unique index and the admin list in one collection.
- **Only the `user` role may report** (`@Roles(Role.User)`). GEN-09 says "a registered user". Admins moderate reports instead of filing them, and moderators manage their provider only, so both get 403. A guest gets 401.
- **Every field is required, `null` included.** `targetType` (`@IsEnum`), `targetId` (`@IsMongoId`) and `reason` (`@IsString`, `@IsNotEmpty`, `@MaxLength`) have no `@IsOptional()`, so a missing field and `null` both answer 400 with the field in `errors`. Unknown fields such as `reporterId` or `status` are refused by the global `ValidationPipe`.
- **The reason is trimmed and has 1 to 500 characters** (`REPORT_REASON_MAX_LENGTH` in `reports.constants.ts`), in the DTO and in the schema. The workbook sets no limit; 500 characters is enough to explain a problem and keeps one request from storing a large amount of text.
- **The server sets the reporter, the status and the dates.** `reporterId` comes from the login cookie, `status` starts as `open` (the schema default), and `createdAt` and `updatedAt` come from `timestamps`. `resolvedBy` and `resolvedAt` from the data model belong to GEN-10 and are added by that PR.
- **The target must be visible to the reporter, otherwise 404.** A post must be published: a draft answers 404 exactly like a missing post, so nobody learns that a draft exists. Another user's itinerary must be public (ITN-20), not hidden by an admin (GEN-10) and its author not deactivated (ACC-12), the same rule as public search (ITN-21); otherwise it answers 404 like a missing itinerary. An id of the wrong type (a post id sent as an itinerary) is a missing target.
- **You cannot report your own content: 400** (`You cannot report your own content`). Reporting yourself is never useful to a moderator, and a 400 tells the frontend to hide the button. The owner always sees their own itinerary, so a private one of their own answers 400, not 404. A draft is treated as missing before the owner check, so your own draft answers 404.
- **At most once per item: the unique index alone.** The unique index (`reporterId`, `targetType`, `targetId`) refuses a second report by the same user of the same item, whether it comes later or at the same moment, and the service turns the duplicate-key error (E11000) into 409 (`You have already reported this item`). There is no read before the insert: it would give the same answer and cost one more database call per report. Other users can still report the same item.
- **Targets are checked through the owning modules' services, not their models.** `ReportsModule` imports `BlogModule` and `ItinerariesModule`. `PostsService.findPublishedAuthorId()` (new, for other services only) returns the author of a published post or `null`. `ItinerariesService.findEntityOrThrow()` already existed and gives the 404 for a missing itinerary. Neither module imports `ReportsModule`, so there is no circular import.
- **Follow-ups (noted in the code too):**
  - Posts have no moderation or author-deactivated field yet, so only `status: published` is checked. When GEN-10 or ACC-12 adds one, `findPublishedAuthorId` must leave those posts out for everyone but the author, as for itineraries; otherwise reporting a hidden post answers 201 instead of 404.
  - The "publicly visible" itinerary rule is written here inline. Once ITN-21 (#167) puts it in `ItinerariesService`, reports should call that method, so search and reports cannot disagree, and read only the fields needed instead of the whole itinerary.
- **The response never names the reporter.** `ReportResponseDto` has `id`, `targetType`, `targetId`, `reason`, `status` and `createdAt` (UTC ISO string). The mapper lists the fields one by one.
- **Indexes:** unique (`reporterId`, `targetType`, `targetId`) for GEN-09, and `status` for the admin list of GEN-10, as in the data model of `specs/travel-platform.md`.
