# reports

Owns the `reports` collection: the `Report` schema, `ReportsService`, the request and response DTOs and the mapper. Requirement: GEN-09 (report content). Route: `POST /api/reports`. Admins list and resolve reports through the `admin` module (GEN-10: `GET /api/admin/reports`, `PATCH /api/admin/reports/:id`); the data access for those routes is here, in `ReportsService`.

## Design decisions

- **Posts and itineraries only, for now.** GEN-09 also names comments and reviews. Comments (BLG-05) were not merged when this was built and hotel reviews are not built yet, so `ReportTargetType` has only `post` and `itinerary`. A later PR adds `comment` and `review` and their visibility checks. No placeholder values were added, so the API never accepts a type it cannot check.
- **`POST /api/reports` is not in section 8 of the project description**, which lists only the admin side (`GET /api/admin/reports`). The route follows the module name and the plural-noun rule of AGENTS.md. One route for every type keeps the unique index and the admin list in one collection.
- **Only the `user` role may report** (`@Roles(Role.User)`). GEN-09 says "a registered user". Admins moderate reports instead of filing them, and moderators manage their provider only, so both get 403. A guest gets 401.
- **Every field is required, `null` included.** `targetType` (`@IsEnum`), `targetId` (`@IsMongoId`) and `reason` (`@IsString`, `@IsNotEmpty`, `@MaxLength`) have no `@IsOptional()`, so a missing field and `null` both answer 400 with the field in `errors`. Unknown fields such as `reporterId` or `status` are refused by the global `ValidationPipe`.
- **The reason is trimmed and has 1 to 500 characters** (`REPORT_REASON_MAX_LENGTH` in `reports.constants.ts`), in the DTO and in the schema. The workbook sets no limit; 500 characters is enough to explain a problem and keeps one request from storing a large amount of text.
- **The server sets the reporter, the status and the dates.** `reporterId` comes from the login cookie, `status` starts as `open` (the schema default), and `createdAt` and `updatedAt` come from `timestamps`. `resolvedBy` and `resolvedAt` from the data model are set by GEN-10 when an admin resolves the report.
- **The target must be visible to the reporter, otherwise 404.** A post must be published: a draft answers 404 exactly like a missing post, so nobody learns that a draft exists. A post an admin hid (GEN-10) answers 404 too, except to its author, who still sees it and gets the 400 below. Another user's itinerary must be public (ITN-20), not hidden by an admin (GEN-10) and its author not deactivated (ACC-12), the same rule as public search (ITN-21); otherwise it answers 404 like a missing itinerary. An id of the wrong type (a post id sent as an itinerary) is a missing target.
- **You cannot report your own content: 400** (`You cannot report your own content`). Reporting yourself is never useful to a moderator, and a 400 tells the frontend to hide the button. The owner always sees their own itinerary, so a private one of their own answers 400, not 404. A draft is treated as missing before the owner check, so your own draft answers 404.
- **At most once per item: the unique index alone.** The unique index (`reporterId`, `targetType`, `targetId`) refuses a second report by the same user of the same item, whether it comes later or at the same moment, and the service turns the duplicate-key error (E11000) into 409 (`You have already reported this item`). There is no read before the insert: it would give the same answer and cost one more database call per report. Other users can still report the same item.
- **Targets are checked through the owning modules' services, not their models.** `ReportsModule` imports `BlogModule` and `ItinerariesModule`. `PostsService.findPublishedSummary()` (for other services only) returns the author and the moderation of a published post, or `null`. `ItinerariesService.findOwnerAndVisibilityOrThrow()` (for other services only) returns the owner of an itinerary and whether it is publicly visible, by ITN-21's own rule (`PUBLICLY_VISIBLE`: public, not hidden, author active), reading only those four fields; it gives the 404 for a missing itinerary. Neither module imports `ReportsModule`, so there is no circular import.
- **Follow-ups (noted in the code too):**
  - Posts have no author-deactivated field yet. When ACC-12 adds one, `findPublishedSummary` must return it too, so reports leave those posts out for everyone but the author, as for itineraries; otherwise reporting such a post answers 201 instead of 404. Hidden posts (GEN-10) are already left out.
- **The response never names the reporter.** `ReportResponseDto` has `id`, `targetType`, `targetId`, `reason`, `status` and `createdAt` (UTC ISO string). The mapper lists the fields one by one.
- **Indexes:** unique (`reporterId`, `targetType`, `targetId`) for GEN-09, and `status` for the admin list of GEN-10, as in the data model of `specs/travel-platform.md`.

## Admin handling (GEN-10)

The routes are in the `admin` module (`AdminModerationController`, see `backend/src/admin/README.md`). This module owns the data, so `ReportsService` has the methods they need, for the admin module only and never used by a controller here:

- **`findEntityOrThrow(id)`**: the report, or 404 "Report not found".
- **`listForAdmin({ status, targetType }, { skip, limit })`**: one page of entities and the total; the admin module maps them with `toAdminReportResponse` and builds the page with `paginate`, like the account list (ACC-14). Oldest first (`createdAt`, then `_id`), because the open list is a work queue and the report that has waited longest should be handled first. `.skip()` is called only past the first page: in earlier local e2e runs against the Atlas test database, a sorted `find` with `.skip(0)` and a filter sometimes never answered, and skipping nothing gives the same result.
- **`resolve(id, status, adminId, resolvedAt)`**: one conditional `findOneAndUpdate` on `{ _id, status: open }`. It returns `null` when the report is no longer open, so of two admins at the same moment only the first one wins and the other gets 409.
- **`changeResolvedStatus(id, from, to)`**: one conditional update of a report that is still `from`. Used when a report claimed as `hidden` turns out to point at content its author deleted in the meantime: it becomes `deleted`.
- **`resolveOpenOfTarget(targetType, targetId, status, adminId, resolvedAt)`**: after content was hidden or deleted, its other open reports get the same status, admin and time in one `updateMany`. The filter always names one item and `status: open`, never a broad set (AGENTS.md "Shared database"). Index: (`targetType`, `targetId`, `status`), new; the unique index starts with `reporterId`, so it cannot serve this filter.
- **The schema gains `resolvedBy` (ObjectId of the admin) and `resolvedAt` (UTC date)**, both empty while a report is open. `ReportAction` (`dismiss`, `hide`, `delete`) and `REPORT_ACTION_STATUS` map an action to the status the report gets (`dismissed`, `hidden`, `deleted`).
- **`AdminReportResponseDto`** extends `ReportResponseDto` with `reporterId` and, once resolved, `resolvedBy` and `resolvedAt` (left out while open). Admins see the reporter; the reporter's own answer (`POST /api/reports`) still never names anyone.
- **Reports are never deleted.** A report of content that was deleted keeps the status `deleted`, as history of what was moderated and why.
